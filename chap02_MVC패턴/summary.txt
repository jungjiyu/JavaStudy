	: 빈 DI ( Dependency Injection 의존성 주입) 시키기 >> @Autowired 
		: 빈에 한해서 동작한다. 직접 생성한 객체에 대해선 동작하진 않는다.
		: 작성 위치
			: https://madplay.github.io/post/why-constructor-injection-is-better-than-field-injection
		********(1) 생성자 Constructor Injection
				:  @Autowired를 명시해주면 param 이 몇 개건 해당 타입의 빈들을 DI 시켜즌다
					: https://www.inflearn.com/questions/140790/%EC%83%9D%EC%84%B1%EC%9E%90-%EC%A3%BC%EC%9E%85%EC%97%90-autowire-%EC%A7%88%EB%AC%B8
				: 해당 클래스가 생성자를 1개만 가지는 경우 @Autowired 명시하지 않아도 자동으로 붙여준다. (2 개 이상인 경우는 x)
				: 제일 권장되는 방법인 이유
					1.  순환 참조상황에서의 호출로 인한 에러 방지 가능 >> 순환 참조가 있을 경우 애초에 실행이 안된다.
						: https://ch4njun.tistory.com/269
						: setter , field injection 의 경우 이를 방지 하지 못한다. (순환 참조 관계가 있어도 실행 자체는 되고, 중간에 순환참조 관계의 객체가 상대 클래스 메서드를 호출했을 때 에러 발생)
						: 순환 참조 >> 클래스A 가 클래스B의 bean 을 주입받고, 클래스B가 클래스A 의 bean 을 주입받는 상황.
							: 순환 참조 자체적으로 에러가 발생되는건 아니고, 순환참조 상황에서 각 클래스에서 상대 클래스의 메서드를 호출할 때 발생한다
 							: 순환 호출이 되면 stackOverflow 발생 >> 클래스A의 메서드가 실행됬다 했을때 내부적으로 클래스B의 메서드가 호출되고 그 내부에서 클래스A의 메서드를 호출하면 끊임없이 호출되기 때문.

						: 생성자 주입에서"만" 이렇게 방지 가능한 원리 >> 빈의 주입 순서 때문. 그러니까 객체 생성에 앞서 빈 생성을 하지 않기 때문
							: A 클래스의 Bean 을 만드는 과정에서 B 클래스의 Bean 을 주입해야되는데 없으니까 B 클래스의 Bean 을 먼저 생성하려한다. 그런데 B클래스에서 A 클래스의 Bean 을 주입하려는데 없으니까 A 클래스의 Bean 을 먼저 생성하려하고 , 이 과정서 또다시 B 클래스의 Bean 주입을 시도한다 . 결과적으로는 무한 반복에 빠지게되어  어떠한 Bean 도 생성하지 못하게 된다.
				

					2. 

				: 주입 순서 
					: 생성자로 객체를 생성하는 시점에 필요한 빈을 주입한다. 조금 더 자세히 살펴보면, 먼저 생성자의 인자에 사용되는 빈을 찾거나 빈 팩터리에서 만든다. 그 후에 찾은 인자 빈으로 주입하려는 빈의 생성자를 호출한다. 즉, 먼저 빈을 생성하지 않는다. 수정자 주입과 필드 주입과 다른 방식이다.
					: 스프링 애플리케이션이 로딩되는 시점에 A 클래스가 B 클래스를 의존하고 B 클래스가 C 클래스를 의존한다면 Spring Boot 는 A 클래스에 대한 Bean 을 만들기 위해서 B 클래스의 Bean 을 주입하는데 없으니까, B 클래스의 Bean 을 먼저 만든다. 근데 그 과정에서 또 C 클래스의 Bean 을 주입하는데 없으니까 C 클래스의 Bean 을 먼저 만든다.

			(2) 수정자 ( setter 계열 메서드 ) Setter Injection
				:  @Autowired를 명시해주면 param 이 몇 개건 해당 타입의 빈들을 DI 시켜즌다
				: 순서
					1. 주입 받으려는 빈의 생성자를 호출하여 빈을 찾거나 빈 팩터리에 등록한다. 
					2. 생성자 인자에 사용하는 빈을 찾거나 만든다. 
					3. 주입하려는 빈 객체의 수정자를 호출하여 주입한다.

			(3) 필드 Field Injection 
				:  @Autowired를 명시해주면 해당 타입의 빈을 DI 시켜즌다
				: 순서
					1.빈을 생성한 후에 어노테이션이 붙은 필드에 해당하는 빈을 찾아서 주입하는 방법이다. 그러니까, 먼저 빈을 생성한 후에 필드에 대해서 주입한다.

							: arg 로 URL 은 "/URL" 의 형식으로 작성하는거 주의

							@RequestMapping("/URL") 
								: 다양한 방식의 request  모두 수용 가능
								: 메서드 뿐 아니라 클래스 자체에도 붙일 수 있다
								: 옵션
									: 같은 URL 주소로의 request 더라도 옵션에 따라서 다르게 mapping 시킬 수 있다.
									1. value >> "/URL" 할당
										: 옵션명 생략 가능>> 옵션이 value 밖에 없는 경우 
										: 다중요청 처리 가능>> {  "/URL1" ,  "/URL2" ,  "/URL3" , ...   } 과 같이 중괄호로 묶은 꼴로 할당
										: 변수 삽입 가능 >>  "/URL"  내부에 { 변수명 } 삽입
										:  정규식 적용 가능
											1. 중간에 삽입되는 변수에 정규식 적용 >> { 변수명:쌩정규식패턴 }
											2. 경로 자체에 정규식 적용 >> 경로 표현 중간에 * , ** , ? 그 자체를 삽입
												* == 해당 레벨의 임의의 디렉터리  ---> "/ ex / * " ,   "/ ex / * / hehe " 
												** == 해당 레벨 이하의 임의의 디렉터리  ---> "/ ex / ** "
												? == 아무거나 한 '문자'  ---> "/ ex?/ hehe"

											: https://wildeveloperetrain.tistory.com/316


									2. method >> RequestMethod.GET , RequestMethod.POST ,  RequestMethod.PUT ,  RequestMethod.PATCH,  RequestMethod.DELETE 중 하나 할당
										
									3. params >> {param1 , param2 .. } 할당
 										: 해당 이름의 parameter 가 전달되어야 mapping 시켜줌

									4. consumes >> MediaType.APPLICATION_JSON_VALUE , MediaType.TEXT_PLAIN_VALUE
										: request header 가 특정 content-type 값을 가져야 mapping 시켜줌
										: MideaType.APPLICATION_JSON_VALUE == application/json
										: MideaType.TEXT_PLAIN_VALUE == text/plan

							@GetMapping("/URL") 
								: get 방식의 request 만 수용
								: !! (클래스 자체에는 못 붙이고) 메서드에만 붙일 수 있다
								: @ReuqestMapping( value= "/URL", method= RequestMethod.GET ) 과 동일

							@PostMapping("/URL") : post 방식으로만 수용
								: post  방식의 request 만 수용
								: !! (클래스 자체에는 못 붙이고) 메서드에만 붙일 수 있다
								: @ReuqestMapping( value= "/URL", method= RequestMethod.POST ) 와 동일
