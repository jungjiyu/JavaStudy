	: 특징 
	1. 제어의 역전 IoC
		: 객체의 생성 및 제어를 사용자가 아닌 스프링이 하는 것
			: 객체의 생성및 제어를 사용자가 하는 것 == new 연산자로 일반 객체 생성하여 활용하는것
			: 스프링이 관리하는 것 == 어노테이션을 활용하여 bean 자동 생성 및 주입 하는 것

		: 조립 이라고도 한다

		: 그러니까 외부 라이브러리의 import 없이, 기본적인 자바 스펙만을 통해 객체를 생성하는 방식을 지향한다는 말

				: @ComponentScan 이 붙은 클래스의 위치를 기반으로(해당 클래스의 패키지 이하에 위치하는) @Component , @Configuration 이 붙은 모든 클래스를 자동으로 scan 하여 스프링 빈으로 등록시킨다.
				: 직접 사용할 일이 별로 없는 이유는 @SpringBootApplication 이 @ComponentScan 을 포함하기 때문.
					: @SpringBootApplication 은 스프링 부트 프젝 생성시 프로젝트의 root 위치 생성되는 기본 클래스에 명시되어있어 기본적으로 우리가 붙이는 @Component 등이 빈으로 등록될 수 있는거다

				: @Configuration 과 함께 사용된다
				: 옵션

	: 빈 DI ( Dependency Injection 의존성 주입) 시키는법 >> @Autowired 이용
		: 빈에 한해서 동작한다. 직접 생성한 객체에 대해선 동작하진 않는다.
		: 작성 위치
			: https://madplay.github.io/post/why-constructor-injection-is-better-than-field-injection
		********(1) 생성자 Constructor Injection
				:  @Autowired를 명시해주면 param 이 몇 개건 해당 타입의 빈들을 DI 시켜즌다
					: https://www.inflearn.com/questions/140790/%EC%83%9D%EC%84%B1%EC%9E%90-%EC%A3%BC%EC%9E%85%EC%97%90-autowire-%EC%A7%88%EB%AC%B8
				: 해당 클래스가 생성자를 1개만 가지는 경우 @Autowired 명시하지 않아도 자동으로 붙여준다. (2 개 이상인 경우는 x)
				: 주입 방식 >> 미리 빈을 만들어두지 않고, 생성자가 실제로 호출되어야 빈을 만들어 주입한다.
				: 제일 권장되는 방법인 이유
					0. setter , field injection과 다르게 해당 필드를 final 로 선언 가능하다 >> immutable 하다

					1.  순환 참조상황에서의 호출로 인한 에러 미리 잡을 수 있다 
						: https://velog.io/@sujin1018/%EC%8A%A4%ED%94%84%EB%A7%81-Spring-%EC%9D%98%EC%A1%B4%EC%84%B1-%EC%A3%BC%EC%9E%85-%EB%B0%A9%EB%B2%95-%EB%B0%8F-%EC%83%9D%EC%84%B1%EC%9E%90-%EC%A3%BC%EC%9E%85-%EB%B0%A9%EB%B2%95%EC%9D%98-%EC%9E%A5%EC%A0%90
						: 근데 어차피 스프링 부트 2.6 부터는 순환 참조 자체를 기본적으로 허용되지 않게 변경되었다고 한다.
						: 순환 참조가 있을 경우 애초에 실행이 안되게 된다.
						: 순환 참조 >> 클래스A 가 클래스B의 bean 을 주입받고, 클래스B가 클래스A 의 bean 을 주입받는 상황.
						: 생성자 주입에서"만" 이렇게 방지 가능한 원리 >> 빈의 주입 방식 차이 때문. 
							:A클래스의 Bean을 만드는 과정에서 B클래스의 Bean이 필요한데 없으니까 B클래스의 Bean을 먼저 생성해야된다. 근데 B클래스는 A클래스를 의존하고 있으므로 A클래스의 Bean을 먼저 만들어야된다.위 상황이 반복되면서 무한 반복에 빠져버리게 되는데, 이렇게 순환되는 과정에서 결과적으로 애초에 Bean도 생성하지 못해서 실행 이전에 오류가 나버린다.
								: 그러니까 수정자/필드 에서는 미리 빈을 만들어두니까 일단 각 arg/필드에 빈을 주입해주는 것까진(일단 실행하는 것까진) 에러가 발생하진 않는데 , 클래스A의 메서드가 실행됬다 했을때 내부적으로 클래스B의 메서드가 호출되고 그 내부에서 클래스A의 메서드를 호출하면 끊임없이 호출되면서 stackOverflow 발생하면 그제서야 에러가 발생한다.

					2. 테스트 코드 작성이 쉽다






			(2) 수정자 ( setter 계열 메서드 ) Setter Injection
				: @Autowired를 명시해주면 param 이 몇 개건 해당 타입의 빈들을 DI 시켜즌다
				: 주입 방식 >> 수정자가 호출되건 말건 일단 arg 로 들어가는 빈을 먼저 만들어두고, 실제로 호출되면 주입시킨다.
				: 해당 필드를 final 로 선언 불가


			(3) 필드 Field Injection 
				: @Autowired를 명시해주면 해당 타입의 빈을 DI 시켜즌다
				: 주입 방식 >> 해당 필드가 쓰이건 말건 일단 해당 타입의 빈을 먼저 만들고 주입한다.
				: 해당 필드를 final 로 선언 불가

						: null 일 경우 예외처리하는 코드 작성가능하다.

					(2) true : 반드시 DI 시키려고하고, 해당 빈이 존재하지 않으면 에러 내버린다 --> 디폴트

							@RequestMapping("/URL") 
								: 다양한 방식의 request  모두 수용 가능
								: 메서드 뿐 아니라 클래스 자체에도 붙일 수 있다
								: 옵션
									: 같은 URL 주소로의 request 더라도 옵션에 따라서 다르게 mapping 시킬 수 있다.
									1. value >> "/URL" 할당
										: 옵션명 생략 가능>> 옵션이 value 밖에 없는 경우 
										: 다중요청 처리 가능>> {  "/URL1" ,  "/URL2" ,  "/URL3" , ...   } 과 같이 중괄호로 묶은 꼴로 할당
										: 변수 삽입 가능 >>  "/URL"  내부에 { 변수명 } 삽입
										:  정규식 적용 가능
											1. 중간에 삽입되는 변수에 정규식 적용 >> { 변수명:쌩정규식패턴 }
											2. 경로 자체에 정규식 적용 >> 경로 표현 중간에 * , ** , ? 그 자체를 삽입
												* == 해당 레벨의 임의의 디렉터리  ---> "/ ex / * " ,   "/ ex / * / hehe " 
												** == 해당 레벨 이하의 임의의 디렉터리  ---> "/ ex / ** "
												? == 아무거나 한 '문자'  ---> "/ ex?/ hehe"

											: https://wildeveloperetrain.tistory.com/316


									2. method >> RequestMethod.GET , RequestMethod.POST ,  RequestMethod.PUT ,  RequestMethod.PATCH,  RequestMethod.DELETE 중 하나 할당
										
									3. params >> {param1 , param2 .. } 할당
 										: 해당 이름의 parameter 가 전달되어야 mapping 시켜줌

									4. consumes >> MediaType.APPLICATION_JSON_VALUE , MediaType.TEXT_PLAIN_VALUE
										: request header 가 특정 content-type 값을 가져야 mapping 시켜줌
										: MideaType.APPLICATION_JSON_VALUE == application/json
