DAO 와 Repository >> 둘다 DB CRUD 하는데 쓰인다.
	: https://velog.io/@mercurios0603/DAO%EC%99%80-Repository%EC%9D%98-%EC%B0%A8%EC%9D%B4

	: 일반적으로 스프링과 JPA를 사용하는 경우, Repository 패턴이 더 선호된다

	DAO Data Access Object 
		: 데이터 영속성을 추상화하는 패턴.  
			: 데이터를 보내고 검색하는 등의 간단한 메소드를 노출하고, 수행하기 위한 복잡한 쿼리를 캡슐화 (내부적으로 감추고) 한다.
		: persistence Layer 에 인터페이스를 제공하고, 그걸 구현하게 한다
		: 좀더 DB스러운 저수준 개념 , lower layer>>  좀 더 유연하고 일반적인. 사용하기 까다로운. 쿼리 사용.
			: DAO가 비록 객체지향적인 인터페이스를 제공하려는 의도를 가지고 있다고 하더라도, 실제 구현 시에는 DAO의 인터페이스는 데이터베이스의 CRUD 쿼리와 1:1 매칭 되는 세밀한 단위의 오퍼레이션을 구현한다
			: persistence Layer 에 속한다
			: DAO 에서 상위 계층인 Repository 의 사용은 불가
		

 	리포지토리
		: 도메인 객체(Entity) 모임을 추상화하는 패턴. 
			:  Domain Layer과 Persistence Layer 사이의 데이터를 대조하고 Domain 객체로 Mapping하는 로직(객체의 Collection을 저장, 검색 하는 등의 동작)을 캡슐화 (내부적으로 감추고) 한다.
				:  Collection >> 도메인 객체(Entity) 모임
		: Repository 인터페이스를 정의하면 스프링 데이터 JPA가 이를 스캔하여 자동으로 데이터 액세스 메서드를 생성하고 관리하기 때문에 직접 구현 클래스를 작성하지 않아도 된다
		: 좀더 도메인 객체에 더 가까운 상위 수준 개념 , higher layer >>더 좁게. 구체적으로 Get(id), Find(Specification), Add(Entity)와 같은 메서드를 사용
			: Domain Layer 에 속한다. 
			: 결과적으로 REPOSITORY에서 제공하는 하나의 오퍼레이션이 DAO의 여러 오퍼레이션에 매핑되는 것이 일반적이다. 따라서 하나의 REPOSITORY 내부에서 다수의 DAO를 호출하는 방식으로 REPOSITORY를 구현할 수 있다.

		: select, insert, update , delete

		: 데이터(테이블)을 저장하거나 객체에 권한을 주는 등의 역할을 하는 언어
		: commit, rollback, grant ( db사용자에게 수행권한 부여) , revoke  ( db사용자의 수행권한 박탈)

		: MySQL , Oracle , MariaDB, H2 등 있다

	: 기본키 Primary key 와 외래키 Foreign Key
		: https://velog.io/@hiy7030/DB-Primary-key%EC%99%80-foreign-key
		: 기본키 PK Primary key >> 해당 테이블 내의 각 레코드의 고유한 식별자
			1. primary key 에 대응하는 값은 null 값 할당이 불가하다
			2. primary key 에 대응하는 값은 레코드간 중복이 불가하다
			3. 보통 하나의 테이블에 하나의 PK 만 가지게 한다 (1개 이상도 가능하긴 하다)	 

		: 외래키 FK Foreign Key >> 일종의 테이블을 연결하는 가상의 다리 역할
			1. 다른 테이블의 PK 에 대응하는 COLUMN . 필드이다.
			2. FK 를 가지는 테이블을 하위테이블, PK 를 가지는 테이블을 상위테이블||참조테이블 이라고 한다
			3. 각 FK 와 PK 는 1:1 매칭되어야된다. PK 에 존재하지 않는 값을 FK 가 가질 수 없다.

	: LOB Long OBject >>  (텍스트. 이미지. 비디오 등)구조화되지 않은 대형 데이터를 저장 목적
		BLOB Binary Long OBject >> 바이너리 기반 데이터 저장 목적
		CLOB Character Long OBject >> 문자 기반 데이터 저장 목적
			: CLOB 와 VARCHAR2 사이에 암시적 변환이 일어난다고 한다

	Entity 엔티티>> DB 테이블에 대응하는 하나의 클래스

		: 관계

			테이블의 record(row)의 집합 ≒ entity의 인스턴스의 집합 ≒ entity   
				: 인스턴스를 entity 라 할 수 있지만 (객체의 집합 이 entity 이므로 원소가 하나인 집합도 entity 다) , entity 를 인스턴스라고 할 수 있을지는 모르는거다(객체의 집합 !=  객체) 
			테이블의 하나의 column ≒ entity의 필드

		: @Entity >> 해당 클래스를 엔티티로 선언한다
			: 그러니까 JPA에 의해 해당 클래스가 RDMS 의 테이블과 매핑되어 DB 구조를 만든다
			: entity 클래스는 보통 entity 패키지에 따로 저장하고, 딱히 XXXEntity 처럼 이름을 짓진 않는다 (그냥 Person , Member 이런식으로 심플 이름).
			: 클래스 제한 사항
			*******0. 테이블에 저장할 필드는 final 키워드 사용 불가
				1. 기본생성자가 있어야된다
					: JPA 도 Reflection API 를 사용하기 때문
				2. final, enum, interface, inner 클래스에는 사용 불가

			: nullable=true 적용 원하는 필드는 reference type 으로 선언해야된다.

			:entity 클래스 내부의 필드는 (@Column 을 명시하지 않아도) 자동적으로 모두 column 으로 간주되고, @Column 의 디폴트 값이 적용된다.
				: 예외 ) nullable 속성 >> @Column 의 nullable 속성의 디폴트 값은 true 이지만, JPA 는 똑똑하게도 필드가 primitive 타입이면 null 값을 가지지 못하는 것을 감안하여 false 값을 적용해준다.
					: 주의 ) @Column 을 명시하는 경우 딱히 primitive type 이런거 인식 안해주고 명시 안된건 걍 default 값 때려버리므로, @Controll 명시할 시 primitive 타입 필드엔 반드시 nullable=false 로 지정해주어야한다.
				: https://ttl-blog.tistory.com/114

			:  name 속성 >> 엔티티 이름을 지정한다
					: 그냥 name 속성을 명시하지 않고 사용 가능하다



		: @Table >> entity 를 db 상에서 어떠한 테이블로 생성할건지(맵핑할건지) 정한다
			: 주로 @Entity 와 함께 쓰이고, 생략 시 엔티티 이름이 테이블명이 된다
			: 속성 
				1. name : 매핑할 테이블 이름 
				2. catalog :  catalog 기능이 있는 데이터베이스에서 catalog 매핑
					: catalog >> 색인. 즉, 데이터베이스의 메타데이터를 저장하는 객체
				3. schema : schema기능이 있는 데이터베이스에서 schema를 매핑한다
					: schema >>도식. 즉, db의 전반적인 명세를 기술한 것.
				4. uniqueConstraints : DDL 생성 시, 유니크 제약조건을 만든다.

		: @Column >> 테이블과 필드를 매핑하기 위해 사용. 해당 필드에 대응하는 column을 생성한다
			: @Entity 내 필드 위에 명시한다
			: 사실 Entity 내부의 모든 필드는 column 으로 간주되기 떄문에 생략해도 무방하나 디폴트 값이 아닌 다른 값으로 설정 원하면 명시해야된다.
			: 속성
				1. name : column 명을 정한다 . 
					: 디폴트값은 필드명이다.
					: db에서는 대소문자 구분이 안되므로 camal 스타일 필드명을 snake 스타일 이름으로 바꿔 저장하는걸 추천
  						@Column(name = "user_nm")

			: value 속성 >> 시간포맷지정. 
				: @Temporal를 아예 명시하지 않은 경우 timestamp 타입으로 매핑되지만, @Temporal 을 명시할 경우 디폴트값이 따로 지정되지 않기 떄문에 (@Temporal 을 명시하면) value 속성 명시는 필수이다
				: 할당 가능한 값
					1. TemporalType.DATE : date 에 매핑 ex) 2023-01-01
					2. TemporalType.TIME : time 에 매핑 ex) 12:03:21
					3. TemporalType.TIMESTAMP : timestamp 에 매핑  ex) 2023-01-01 12:03:21

			: ex) 
				@Temporal(TemporalType.TIMESTAMP)
				private Date createdDate;

		: @Enumerated >> 자바의 enum 타입을 매핑할 때 사용
			: value 속성 >> 저장할 값 지정. 
				: 할당 가능한 값
					1. EnumType.ORDINAL : enum 순서를 db에 저장 
					2. EnumType.STRING : enum 이름을 db에 저장 
						:EnumType.ORDINAL 보다 권장된다 --> enum 의 순서가 변경되거나 중간에 새 내용 추가됬을떄 db의 기존 데이터와 일치하지 않게 될 수 있어서

		: @Lob >> BLOB, CLOB 타입과 매핑
			: 매핑하는 필드 타입이 문자면 CLOB 으로, 그 외의 타입이면 BLOB 로 자동 매핑된다
				ex) 
					@Lob 
					private String lobString; // CLOB으로 매핑
 
					@Lob 
					private byte[] lobByte; // BLOB으로 매핑

				2. AccessType.PROPERTY : getter 를 통해 접근
