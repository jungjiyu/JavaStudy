헷갈리는거 정리
	(1) PK&FK 와 JOIN
	    : PK&FK >> 테이블끼리 관계 맺어두는것
	    : JOIN >> 두 테이블을 합쳐서 조회하는 것
		개발자가 날리는 경우 : 
			(1) 상속관계 테이블을 조회할 때
			(2) 연관관계 테이블을 조회할 때

		jpa 가 날리는 경우 : 
			(1) 상속관계 테이블을 조회할 때.
				SELECT 부모테이블.* , 자식테이블.* 
					FROM 부모테이블 
					JOIN 자식테이블 
						ON 부모테이블.PK = 자식테이블.PK;

			(2) LAZY 로딩이 아닌 상황에서, 연관관계 객체를 조회할 떄.
				SELECT 참조하는테이블.* , 참조당하는테이블.* 
					FROM 참조하는테이블 
					JOIN 참조당하는테이블 
						ON 참조하는테이블.PK = 참조당하는테이블.FK;


				: 주의 >> LAZY 로딩인 상황에선, join 문이 아닌 일반 select 문이 날라간다.

	(2) 상속관계와 연관관계
		: 상속관계 >> 데이터베이스 설계에선 직접적으로 존재하지 않지만,  객체 지향 프로그래밍의 상속 개념을 흉내내는 것.
		: 연관관계 >> 1대1 , 1대 다 같은 개념


	(3) A 를 투명 transparent 하게 처리한다 == 별도의 추가적 코드 없이, A 과정이 자연스럽게 이뤄진다.

	(3)  A 가 B 를 추상화했다== B를 좀 더 간단히 사용 가능하도록, A를 구현할 때 내부적으로 B를 활용하게 미리 다 짜놨다. 
		: ex ) Spring Data JPA 는 JPA를 추상화한 것이다.
			: Spring Data JPA 를 활용하면 , 직접 entity manager 수준에서 작업하지 않고 간단하게 메서드를 사용하여 그 기능을 구현할 수 있다.


	(4) 표준 명세 >>특정 인터페이스, 기술, 프로토콜 등에 대한 규칙과 요구 사항을 "정의"하는 문서
		: ex ) JPA 
		: 다양한 구현체들이 일관되게 동작할 수 있도록 하기 위한 규범을 제공한다
		: 표준 명세도 import 할 수 있다.
			: 라이브러리만 import 할 수 있는게 아니다.

	(5) 라이브러리 >> 특정 "기능"을 쉽게 구현할 수 있도록 미리 작성된 코드의 모음. 
		: ex ) Hibernate
		: 주의 >> 라이브러리에는 구현체(class)가 있어야된다
			: 표준 명세 != 라이브러리 >> 표준 명세는 구현체가 없으니까


	(6) 프레임워크 >>  애플리케이션의 "구조""를 정의하고, "개발자"가 그 구조에 "따라" 애플리케이션을 개발하도록 돕는 도구
		: 제어의 역전 IoC 가 일어난다 >> 개발자가 프레임워크가 요구하는 방식으로 코드를 작성한다
		: 라이브러리가 특정 기능의 모음이라면, 프레임워크는 구조||환경를 정의한 것이다.

	(7) 모듈 >> 독립적 실행, 재사용 가능한 코드 묶음
		: 라이브러리를 그룹화한게 모듈
		: 모듈은 프레임워크의 내부에서 동작하게 된다.

자바로 개발하는 대부분의 어플리케이션은 RDB 를 데이터 저장소로 사용하고, 그를 활용하기 위해 SQL 문을 사용함. 자바로 작성한 애플리케이션은 JDBC API 를 사용해서 SQL 을 db에 전달.

SQL 에 의존적이다 : 객체의 수정사항이 있을 때 , 개발자가 직접 SQL 문을 수정해야한다.

SQL 을 직접 다룰때의 문제점 : 
	(1) 매번 직접  mapper 역할을 해야됨: 애플리케이션의 객체와 db 의 데이터의 구조가 다르기 떄문에 개발자가 중간에서 변환작업( 데이터 받고, 객체에 일일이 매치시켜주고. 객체에서 일일이 데이터 꺼내서, 그걸로 쿼리문 날리고. )을 직접 해줘야된다.
	(2) 유지보수가 어렵다 : 객체에 필드를 추가하면, 자동적으로 이전에 DAO 단에 작성된 쿼리문들까지 수정되는게 아니라 일일이 고쳐줘야된다.
	(3) 진정한 계층 분할이 이뤄지지 않는다. : 물리적으로는 SQL 과 JDBC API 를 데이터 접근 계층에 숨기는데 성공했을지 몰라도, 논리적으로는 엔티티와 아주 강한 "의존"관계를 가지고 있다.
		: 그러니까 , 객체가 어떻게 구성되있건 sql 문에 따라 어떻게 작동될지 갈려서 엔티티를 신뢰할 수 없고, dao 를 일일이 열어 어떤 sql 이 실행되는지 확인해야된다. 
	(4) 엔티티 신뢰 불가 
	(5) sql 의존적 개발

			: 테이블 차원 >> FK 와 PK 기반

					SELECT TEAM.* , MEMBER.*

					SELECT TEAM.* , MEMBER.*

							ON MEMBER.ID = TEAM.ID;

테이블의 경우 MEMBER JOIN TEAM 이든 TEAM JOIN MEMBER 든 둘 다 가능하다

							Member member = new Member( ); // 참조하는 객체 생성

							member.setTeam( team ); // 객체간 연관관계 생성


						step1.  참조필드를 가지는 객체의 id 필드로 PK 값 얻어낸다.
						ex ) Long pk = member.getId( ); 

						step2.  참조필드를 가지는 객체의 참조필드에서 참조당하는객체를 뽑고, 그 객체애서 id 값을 또 뽑아서 FK 값 얻어낸다. 
						ex ) Long fk = member.getTeam( ).getId( );

					: 테이블 --> 객체
						step1. 참조를하는테이블과 참조당하는테이블을 join 해 얻어옴.
						ex ) SELECT TEAM.* , MEMBER.* 
								FROM MEMBER   
								JOIN TEAM  
								ON MEMBER.ID = TEAM.ID;

						step2. 쿼리 결과에서 데이터 뽑아서 참조당하는 객체 생성 및 초기화

						ex )
							 Team team = new Team( );
							 team.setId( 쿼리결과에서추출한아이디값 );
							 team.setName( 쿼리결과에서추출한이름값 );

						step3. 쿼리 결과에서 데이터 뽑아서 참조하는 객체 생성 및 앞서 생성한 참조당하는 객체도 활용하여 초기화

						ex ) 
							 Member member = new Member( );
							 member.setId( 쿼리에서추출한아이디값);
							 member.setTeam( 앞서생성한Team객체 );

	

				sol2. JPA 사용 >> ㅈㄴ 좋음
					: 객체 --> 테이블 
						step0. 연관관계 가지도록 객체 생성 및 초기화
							ex) 이건 sol1 과 같음
						step1. 참조하는객체를 걍 persist( )로 저장
							: 이케하면 JPA 가 알아서 참조필드를 FK 로 변환해서 적절한 insert 문을 작성해준다. 
							ex ) jpa.persist( member );
 
					: 테이블 --> 객체
						step1. 참조하는객체를 걍 find( ) 로 조회
							: 이케하면 JPA 가 알아서 FK 컬럼을 참조필드로 변환해 객체 생성시켜준다.
							: 기본적으론 지연로딩을 사용하기 때문에, 당장은 "SELECT 참조객체테이블 ..." 만 실행한다 (JOIN 문 쓰는게 아니다)   
							ex ) Member member = jpa.find( Member.class , memberId );

						step2. 참조당하는객체를 조회된 객체에서 꺼내서 씀
							: JPA 가 그에 대응하는 쿼리문인 "SELECT 참조당하는객체테이블 ..." 을 새로 작성해서 날린다. 
							ex ) Team team = member.getTeam( ) ;

		(3) 객체 그래프 탐색 >> 객체끼리 가지는 참조 관계로 건너 건너 객체를 얻는 것. 얘도 결국 연관 관계에 대한 건데, 좀 긴(?) 걸 말하는 거임.
			: 객체 차원>> 당연히 가능
				ex ) Member 클래스에 Team 필드가 있고, Team 클래스에 Nation 필드가 있다하자. 그럼 Member 객체로 Team 객체를 얻을 수 있고 , 그 Team 객체로 Nation 객체를 얻을 수 있다.

			: 테이블 차원>>  어떤 JOIN 문을 사용하였느냐 따라 가능하기도 하고 불가능하기도 하다. SQL 문을 직접 다루면, 처음 실행된 SQL문에 따라 객체 그래프를 어디까지 탐색할 수 있는지 한정된다.
				ex ) Member 테이블과 Team 테이블을 JOIN 하여 쿼리문을 작성한 경우, 반환결과에서 team 객체까지는 얻을 수 있지만 , 쿼리문에 명시되지 않았던 Nation 과 같은 객체는 얻을 수 없다.

			: 문제점 >>  직접 쿼리문을 다루면 비즈니스 로직 수행할 때 어디까지 객체 그래프를 탐색가능한지 SQL 문을 까지 않는 이상 확신이 불가하다.(= SQL 문에 의존적.)

			: 해결방법 >> 단순개발자 차원에선 해결이 불가(매번 해당 객체와 관련된 모든 객체를 쓸지 안쓸지도 모르는데 불러오는건 손해). JPA 로만 해결가능
				: JPA 로 객체를 조회하면,  이후 (별도의 처리 없이도) 해당 객체와 연관된 객체를 사용할때 JPA가 알아서 관련 select 문을 실행시켜준다. 
					: 따로 설정을 통해 매번 해당 객체와 관련된 객체를 불러오게 할 수도 있다.


		(4) 비교 . 구별 >> 
			: 객체 차원 >> 동일성과 동등성 측면 비교.
				1. 동일성 identity : "==" 를 통한 비교. 즉 , 아예 물리적으로도 같은 객체인지(주소 같은지)를 판단.
				2. 동등성 equality : ".equals( )" 를 통한 비교. 즉, 논리적으로 같은 내용을 담은 객체인지 판단. 
			: 테이블 차원 >> PK 컬럼의 값으로 각 row 를 구분. 
			: 문제점 >> 직접 쿼리문으로 조회하여 객체를 얻는 경우, 같은 row 대해 select 한 것이라도 각각 다른 객체로 인식된다.
			: 해결방법 >> JPA 를 사용하여 객체를 얻는다.
				: JPA 는 같은 트랜잭션일 때 같은 객체가 조회되는 것을 보장한다.
				: 더 자세한 내용은 이후 챕터에서...

DDL ( Data Definition Language) : 데이터베이스 스키마를 정의하는 일련의 SQL 명령

DBMS Database Management System : 데이터베이스를 운영하고 관리하는 소프트웨어
	: Oracle,  MySQL 등



JDBC Java Database Connectivity : "통일된" 인터페이스로 자바 어플리케이션에서 "DB에 접근"할 수 있도록 하는 규약이자 API
	: https://velog.io/@kkimbj18/JPA-%EA%B8%B0%EB%B3%B8-%EA%B0%9C%EB%85%90%EA%B3%BC-%EC%82%AC%EC%9A%A9-%EC%9D%B4%EC%9C%A0-Feat.-JDBC
	: 원리 >>JDBC 드라이버 활용 . 
	    	: JDBC 드라이버 >> DBMS 회사들이 해당 제품을 간단히 사용 가능하도록 구현하여 제공하는 인터페이스.
			: 어떤 DBMS 를 이용하던 JDBC 드라이버만 다르고, 동일한 JDBC API 를 사용한다.
		: 주의 >> 그렇다고 완전히 DBMS 의 영향을 안받는건 아님. JDBC 활용 위해 직접적인 SQL 쿼리문 작성이 필요하기 때문. ( 뭐 대부분은 표준 SQL 문이긴 한데, 특정 문법은 DBMS 따라 좀 다른 것도 있다 )

	: 참고 JDBC API == JDBC . 
		: JDBC 는 큰 개념적인거고, JDBC API 는 실제로 JDBC 기능을 하는 클래스, 메서드등의 집합을 말한다.




ORM Object Relational mapping : 객체와 관계형db를 매핑해주는 기술. 객체와 관계형 데이터베이스 간의 차이를 중간에서 해결주는 기술. 
	: ORM 프레임워크의 "성숙도" 따라 패러다임 불일치 문제까지 해결해주는 기능이 있기도 없기도 함.
	: ORM vs SQL mapper 
		: ORM 은 객체와 테이블을 매핑하고, SQL mapper 는 객체와 SQL 문을 매핑한다.  >> 객체의 수정사항이 있을 시 개발자가 직접 SQL문을 일일이 수정해야하므로 SQL mapper 는 SQL 의존적이다. 


JPA Java Persistence API : 자바 진영의 "ORM" 기술에 대한 API 표준 명세.
	: 효과
		1. 객체지향적 개발 가능 : SQL 문을 개발자가 직접 사용하지 않고, 객체 지향적 코드 쓰면 알아서 SQL 문으로 변환한다.
		2.  필요 따라 DDL 문을 자동 생성해준다
		3. 유지보수 용이하다 : 필드 수정 시 JPA 가 알아서 수정해준다.
		4. 패러다임 불일치 해결
		5. 성능개선 : 재사용 기능이 있어 경우 따라선 조회할 떄마다 통신하지 않는다. 
		6. 특정 dbms 에 종속적이지 않은 개발이 가능하다 : dbms 바꿀 땐 큰 수정 필요 없이 단순 JPA 에게 다른 db 쓴다고 알려줌 된다.

	: "자바 애플리케이션"과 "JDBC 사이"에서 동작하고, 객체지향적 개발을 가능하게 해준다.
		: 객체지향적코드 <---> SQL 문의 전환은 JPA 가.
		: SQL 문으로 DB와 통신하는건 JDBC 가.





	: JPA vs Hibernate vs Spring Data JPA
		: https://suhwan.dev/2019/02/24/jpa-vs-hibernate-vs-spring-data-jpa/
		: JPA >> 말 그대로 "표준 명세" 즉, 인터페이스이지 , 라이브러리가 "아니다"
 			: JPA 가 정의된 javax.persistence.* 에는 interface , enum, Exception, Annotation 은 있지만 구현체는 없다.
		: Hibernate >>JPA 의 구현체, 즉 라이브러리
			: JPA 의 구현체는 여러개 있지만, 그중 Hibernate 가 가장 유명.
			: Hibernate 는 거의 대부분의 패러다임 불일치를 해결가능한, 성숙한 ORM 라이브러리이다
		: Spring Data JPA >> JPA 를 더 편하게 쓰기 위한 모듈
			:  Spring에서 제공한다.
			:  JPA를 한 단계 더 추상화시킨 XXXXRepository 인터페이스를 제공
				: 직접 entity manager 수준 작업하지 않아도 된다.
				:  사용자가 Repository 인터페이스에 정해진 규칙대로 메소드를 입력하면, Spring이 알아서 해당 메소드 이름에 적합한 쿼리를 날리는 구현체를 만들어서 Bean으로 등록해준다


	:  역사 : EJB 등장 >> hibernate 등장 >> JPA 등장 
		1. EJB Enterprise Java Beans 엔터프라이즈 자바 빈즈 등장: 자바진영이 발표한 기술 표준으로, "엔티티 빈"이라는 ORM 기술을 포함했으나, 이는 사용하기 어렵고 실용성이 떨어졌다.

		2. hibernate.org ( 라는 오픈소스 ORM 프레임워크 ) 등장 : EJB 의 ORM 기술(엔티티빈)에 비해 사용하기도 쉽고, 실용성도 뛰어났다.

		3. JPA 등장 : EJB 가 hibernate 기반으로 새롭게 만든  자바 진영의 "ORM" 기술에 대한 API 표준 명세.


	: JPA 에서의 "매핑정보" >> 어떤 객체를 어떤 테이블에 관리할지 정의한 정보

	: JPA 를 사용하면 
	: JPA 가 제공하는 API 를 사용한다
		(1) 저장 : .persist( 엔티티객체 )
 			:  JPA 가 객체와 매핑정보를 보고, 적절한 insert SQL 문을 생성하여 db 에 전달한다
				ex ) 
					Member member = new Member("jojo123" , "jojo");
					jpa.perisit(member); // 생성

		(2) 조회 : .find( 엔티티클래스명.class , 엔티티의특정필드값 )
			: JPA 는 객체와 매핑정보를 보고 적절한 select SQL 문을 생성해서 db에 전달하고, 그 결과로 해당 엔티티타입의 객체를 생성하여 반환한다.
				ex ) 
					String memberId = "jojo123"; 
					Member member = jpa.find( Member.class , memberId );  // 조회

			: 같은 트랜잭션에서 같은 row 대해 find 하면, 같은 객체가 조회되는 것을 보장한다.
				: 객체의 동일성. 동등성 비교 측면에서 간편하다. 이후 챕터에서 계속... 
	

		(3) 수정 : 별도의 메서드 X
			: JPA는 별도의 수정 메서드를 제공하지 않는다. "조회( find )해서 얻은" 객체를 수정하면 트랜잭션을 commit 할 때, db에 적절한 update SQL 문이 전달된다.  << 3장 자세히
				ex ) 
					Member member = jpa.find( Member.class , memberId ); 
					member.setName("johojoho"); // 수정 

		(4) 연관된 객체 조회  : 별도의 메서드 X
			: 연관된 객체를 "사용"하는 시점에 적절한 select SQL 문을 실행한다. << 8장자세히
				ex ) 
					Member member = jpa.find( Member.class , memberId );  // SELECT MEMBER .. 만 실행한다
					Team team = member.getTeam( ) ; //  SELECT Team ..은 이제서야 실행한다.


			: 미리 불러놓지 않고, 이렇게 필요할 떄 다 되서야 불러오는걸 "지연로딩" 이라고 한다
				: JPA의 지연로딩은 투명 transparent 하게 처리한다. (별도의 추가적 코드 없이 진행됨.)

			: 지연로딩이 디폴튼데, 이를 사용하지 않고 매번 미리 불러놓도록 설정할 수도 있다.
				: 이 경우 아래와 같은 쿼리문이 실행된다
				SELECT 참조하는테이블.* , 참조당하는테이블.* 
					FROM 참조하는테이블 
					JOIN 참조당하는테이블 
						ON 참조하는테이블.PK = 참조당하는테이블.FK;
