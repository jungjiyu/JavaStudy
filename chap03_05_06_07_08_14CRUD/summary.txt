redirect 
	: 클라이언트에게 '특정URL'을 response 후, 클라이언트가 자동적으로 해당URL을 후속 request 하여 또다른 response 를 받게 하는 문자열.
	: 리다이렉트를 언제, 왜 쓰는가?  >> 반복되면 안되는 로직을 수행하는 메서드( 주로 post 와 맵핑되어있는)의 리턴값으로 쓴다.
		1. POST 방식이든 GET 방식이든 새로고침 하면 해당 방식으로 또 request 된다. 브라우저에서 새로고침이나 뒤로 가기를 했을 경우 이전에 보내진 POST 요청이 다시 보내져(== 결제 로직이 또 진행되어) 중복 결제와 같은 버그가 일어날 수 있다.
		2. POST 요청은 URL을 복사하더라도 다른 사람과 공유할 수 없다

		: PRG 패턴 >> POST 방식으로 온 요청에 대해서 GET 방식의 웹페이지로 리다이렉트 시키는 패턴
			:  Post 방식으로 온 request 대해서 , 리다이렉트하도록 response 하고, reponse 받은 경로로 get 방식 request 하는 것	
			: https://programmer93.tistory.com/76



	: "redirect:/경로"
	: 리다이렉트 원리
		1. 클라이언트에게 특정 리다이렉트경로를 response 한다
		2. 클라이언트가 response받은 경로 ( 리다이렉트하라는 경로) 로 get 방식으로 request 한다
		3. request 한 경로로 getMapping 된다

	: 리다이렉트 할 떄 해당 메서드에서 받은 데이터를 전달하고 싶으면 param 에 별도로 RedirectAttributes 추가
		: RedirectAttributes 메서드
			: 리다이렉트값을 리턴하는 메서드( PpstMapping ) 에서 addAttribute||addFlashAttribute 로 저장하고, 리다이렉트 결과로 맵핑된 메서드 ( GetMapping ) 에서 이를 받아서 @RequestParam 혹은 @ModelAttribute 로 받아서 활용한다.
			1. addFlashAttribute( ) : 일회성으로 값을 전달 시 사용
				: 애플리케이션의 session 객체에 저장하고, 다음 요청에서만 접근 가능하게 한다
					: 클라이언트쪽에 리다이렉트 경로와 함꼐 response 하는게 아니라, 애플리케이션 상에서만 접근 가능한 것이다.
					: 다음 요청 이후엔 자동으로 삭제된다. ( 심지어 새로고침 해도 없어짐 !)
				: String 타입 값 뿐 아니라 다양한 타입 값을 전달 가능하다
				: 주소 창에 표기되지 않으므로 addAttribute( ) 보다 보안이 좋다
				: 리다이렉트 되어 @GetMapping된 다음 메서드의 model 객체에 자동 등록된다
					: 직접 파라미터에 model 객체를 만들어주지 않아도, 리다이렉트된 메서드에서 model 객체를 자동 생성해서 addAttribute 해준다.
					: getMapping 되어 이동한 페이지에서 addFlashAttribute( )  할 떄 저장했던 변수명으로 뷰페이지에서 사용 가능하다
				: 경고/완료 메세지 보낼때 유용하다


			2. addAttribute( ) : 값을 지속적으로 전달 시 사용
				: URL 뒤에 값을 추가하여 클라이언트에게 response 하고, 그 값을 다시 클라이언트가 URL 뒤에 추가하여 해당 경로로 request 하게 한다
				: 리다이렉트되어 @GetMapping 된 다음 메서드에서는 해당 attribute 을 일반적으로 넘어오는 값과 마찬가지로 @ReqeustParam 을 이용하여 받을 수 있다 >> URL 뒤에 추가되어 전달되는 String 타입 값이기때문

Iterator 인터페이스
	: 모든 컬렉션 프레임워크에 공통으로 적용 가능한 메서드들을 보유하고 있는 인터페이스
		: Collection 과 딱히 상속 관계 없지만, 컬렉션 객체들은 모두 .iterator( ) 를 통해 Iterator 객체화가 가능하기 떄문에 가능

	: 주로 컬렉션 프레임워크를 표준화된 방법으로 읽기 위해(순회위해) 사용

	: Iterator객체 생성 방법
		Iterator<T> 변수명 = 컬렉션객체명.iterator( );

	: Iterator 객체를 대상으로 사용하는 메서드
		boolean hasNext( ) : Iterator 에 다음 값이 들어있는지 확인
		Object next( ): Iterator 에서 다음값 가져옴 
		void remove( ): next( ) 로 읽어온 값을 컬렉션 상에서 삭제
			; 주의  ) next( ) 를 실제로 호출한 뒤 바로 뒤에서 remove( ) 해야 반영된다
		
	: 주의(단점)
		0. 한번 사용된 Iterator 객체는 재사용 불가. (한번 next( ) 로 모든 요소를 다 읽으면 그다음엔 더 읽을게 없어짐)
		1. 처음부터 끝까지의 단방향 반복만 가능
		2. 대상 "컬렉션 객체" 상의 값의 제거는 가능하나 추가가 불가

Collection 인터페이스
	: (List 와 Set의 ) 실질적인 최상위 인터페이스 (다형성 구현)
	: 메서드
		: get 기능은 Collection 인텊페이스에 구현되어있지 않다. (각 컬렉션마다 자료구조가 제각각)
		boolean add(Object o) : 객체를 해당 컬렉션의 요소로 추가
		boolean addAll(Collection c) : 다른 컬렉션의 모든 요소들을 해당 컬렉션의 요소로 추가

		boolean contains(Object o) : 해당 객체를 포함하고 있나 확인
		boolean isEmpty( ) : 해당 컬렉션이 비어있는지 확인
		int size( ) : 컬렉션에 저장된 요소 수 반환

		boolean remove(Object o ) : 해당 객체를 컬렉션에서 삭제
		boolean removeAll(Collection c ) : 다른 컬렉션에 포함된 모든 요소를 해당 컬렉션에서 삭제
		void clear()	: 해당 컬렉션에서 모든 요소 삭제

		Iterator iterator( ) : 해당 컬렉션 객체를 iterator 객체로 반환 


List 인터페이스 :  순서가 있고 중복을 허용하는 데이터 집합.
	: 메서드
		void add(Object elmt ) : 제일 끝에 요소 "삽입"
		void add(index , Object elmt ) : 해당 인덱스에 요소 "삽입"
		Object set(int index , Object elmt) : 해당 인덱스를 해당 요소로 "변경"  
		Object get( int index ) : 해당 인덱스의 요소 반환
		Object remove(int index) :해당 인덱스의 요소 삭제 및 삭제된 객체 반환

		int indexOf( Object o ) : 해당 객체의 인덱스 반환

	:  XXXXDTO.java 를 보통 클래스 명으로 한다
		: 구성
			1. private 필드
			2. 기본생성자 << 필수
				: DTO 의 기본생성자와 getter/setter 가 필수인 이유 >> Reflection API 
					: Reflection API >> 자바에서는 JVM이 실행되면 작성된 자바 코드가 static 영역에 저장된다. Reflection API는 이 정보를 활용하여 구체적인 클래스 타입을 알지 못해도 클래스 이름을 통해 static 영역에서 그 클래스의 정보(메서드, 타입, 변수 등등)에 접근할 수 있게 해준다.
						: @RequestBody 나 JPA 에 Reflection API 가 사용되고, Reflection API 는 생성자와 getter 를 필요로 한다고 한다.
			3. getter / setter << 필수
			4. toEntity( ) 구현 
				    public 엔티티타입 toEntity() {
				        return new 엔티티타입( this.id, this.입력가능필드1 , this.입력가능필드2 , ..);
  				  }

				: JPA 사용시 DTO객체를 entity 객체로 변환하는 역할이다
				: 내부적으로는 해당 DTO 객체의 필드를 entity클래스의 생성자의 arg 로 하여  entity클래스객체를 생성하여 반환한다
					: 일단 해당 entity클래스가 존재해야 사용 가능하므로, entity 클래스를 먼저 만든 후 작업한다.
						: 해당 entity 클래스에 엔티티타입( this.id, this.입력가능필드1 , this.입력가능필드2 , ..) 꼴의 생성자를 만드는 거 잊지 말아야된다
					: entity 만들때 ( 시간처럼 자동생성 되는 값을 할당받는 필드가 아닌 ) 입력해야되는필드( name , phone 같은)와  id필드를 arg 로 해야된다.
						: 해당 dto 객체가 별도로 값을 입력받지 못해 필드가 null 값인 상태로 entity 객체를 생성할 경우 , 즉  new 엔티티타입( null , 값1 , null  , ..) ; 꼴 인경우 ,  null 값애 대응되는 엔티티의 필드는 엔티티 클래스의 default 값이 적용된다. (에러가 나진 않는다.)
						: id 필드도 arg 로 하는 이유는 , 그 id 를 가지는 객체를 생성해 db 에 반영하겠단 의도가 아니라 ( id 는 대부분 auto increment ) , 그냥 계층간 데이터 전송할 때 id 값도 많이 필요로 하니까 편의성 차원에서 넣어두는 거다. 
							: 새로운 record 생성 위해 클라이언트로부터 데이터를 dto 객체로 받을 때는 id 값을 따로 받지 않으므로 id 필드는 null 값이고, new 엔티티타입( null , 값1 , 값2  , ..) ; 의 꼴이 되어 id 는 entity 클래스 측의 auto 값이 적용된다.

	DAO Data Access Object 
		: 데이터 영속성을 추상화하는 패턴.  
			: 데이터를 보내고 검색하는 등의 간단한 메소드를 노출하고, 수행하기 위한 복잡한 쿼리를 캡슐화 (내부적으로 감추고) 한다.
		: persistence Layer 에 인터페이스를 제공하고, 그걸 구현하게 한다
		: 좀더 DB스러운 저수준 개념 , lower layer>>  좀 더 유연하고 일반적인. 사용하기 까다로운. 쿼리 사용.
			: DAO가 비록 객체지향적인 인터페이스를 제공하려는 의도를 가지고 있다고 하더라도, 실제 구현 시에는 DAO의 인터페이스는 데이터베이스의 CRUD 쿼리와 1:1 매칭 되는 세밀한 단위의 오퍼레이션을 구현한다
			: persistence Layer 에 속한다
			: DAO 에서 상위 계층인 Repository 의 사용은 불가
		

 	리포지토리
		: 도메인 객체(Entity) 모임을 추상화하는 패턴. 
			:  Domain Layer과 Persistence Layer 사이의 데이터를 대조하고 Domain 객체로 Mapping하는 로직(객체의 Collection을 저장, 검색 하는 등의 동작)을 캡슐화 (내부적으로 감추고) 한다.
				:  Collection >> 도메인 객체(Entity) 모임
		: Repository 인터페이스를 정의하면 스프링 데이터 JPA가 이를 스캔하여 자동으로 데이터 액세스 메서드를 생성하고 관리하기 때문에 직접 구현 클래스를 작성하지 않아도 된다
		: 좀더 도메인 객체에 더 가까운 상위 수준 개념 , higher layer >>더 좁게. 구체적으로 Get(id), Find(Specification), Add(Entity)와 같은 메서드를 사용
			: Domain Layer 에 속한다. 
			: 결과적으로 REPOSITORY에서 제공하는 하나의 오퍼레이션이 DAO의 여러 오퍼레이션에 매핑되는 것이 일반적이다. 따라서 하나의 REPOSITORY 내부에서 다수의 DAO를 호출하는 방식으로 REPOSITORY를 구현할 수 있다.

		: 기본키 PK Primary key >> 해당 테이블 내의 각 레코드의 고유한 식별자
			1. primary key 에 대응하는 값은 null 값 할당이 불가하다

			3. 보통 하나의 테이블에 하나의 PK 만 가지게 한다 (1개 이상도 가능하긴 하다)	 

		: 외래키 FK Foreign Key >> 일종의 테이블을 연결하는 가상의 다리 역할
			1. 다른 테이블의 PK 에 대응하는 COLUMN . 필드이다.
			2. FK 를 가지는 테이블을 하위테이블, PK 를 가지는 테이블을 상위테이블||참조테이블 이라고 한다
			3. 각 FK 와 PK 는 1:1 매칭되어야된다. PK 에 존재하지 않는 값을 FK 가 가질 수 없다.

관계의 종류 >> 기수 Cardinality  + 필수여부 Optionality 
	Cardinality 
		(0) 일 대 일 관계 ( 1 : 1 ) >> 테이블A의 하나의 레코드가 테이블B의 레코드 한 개와만 연결되어있고 테이블B의 하나의 레코드도 테이블A의 레코드 한 개와만 연결되어있을 떄
			ex) 한 사람은 고유한 전화번호를 갖는다

		(1) 일 대 다 관계 ( 1 : n ) ,  다 대 일 관계 ( n : 1 ) >> 테이블A의 하나의 레코드가 테이블B의 여러 레코드와 연결되어있고, 테이블B의 여러 레코드가 테이블A의 레코드에 연결되어있을 때
			ex) 한 사람은 여러개의 전화번호를 가질 수 있지만, 하나의 전화번호를 여러 사람이 가지진 못한다.
			ex ) 한 저자는 여러개의 댓글을 쓸 수 있지만, 한 댓글은 한 저자에 의해서만 쓰여질 수 있다

		(2) 다 대 다 관계 ( n : m ) >> 테이블A 의 하나의 레코드가 테이블B의 여러 레코드와 연결되어있고, 테이블 B의 하나의 레코드도 테이블A의 여러 레코드와 연결되어있을 떄

	Optionality 
		(1) Optional 있을수도 없을 수도
			ex ) 저자는 댓글을 쓸 수도 쓰지 않을 수도 있따

		(2) Mandatory 필수적
			ex ) 댓글은 필수적으로 저자가 존재한다


관계의 표현 >> PK 와 FK 의 연결로 표현됨
	: 부모테이블과 자식 테이블
		부모테이블 >> PK 쥐는 테이블 . 자식 테이블과 상관 없이 독립적으로 존재 가능하다
		자식테이블 >> FK 쥐는 테이블. 부모 테이블에 의존적이다. 

	: FK
		: 한 테이블은 여러개의 FK 를 가질 수 있다.  ( 부모 여러명 가능 )
		: FK 인 Column 명이 꼭 부모 테이블의 PK 명과 똑같을 필욘 없고, 맥락상 이해가 가는 정도로만 작명하면 된다.
			ex) User 테이블과 Comment 테이블 은 1:n 관계 이고 각각 id column 을 PK 로 한다고 하자. User 테이블과 Comment 테이블은 1: n 관계이므로 Comment 테이블은 User 테이블의 id column 을 FK 로 가져야되는데 그 이름 그대로 쓰면 Comment 테이블 자신의 id column 과 column 명이 겹치므로 user_id column 으로 작명하여 FK 를 마련한다.


	(1) 1:1 관계 >>  1:1 관계에서는  의존적인 테이블을 판단하여 FK 를 준다 

	(2)  1:n 관계 >> n 쪽에 FK 를 주면 된다

	(3) n : m 관계 >> 양 테이블의 PK 를 FK 으로 가지는 "mapping 테이블"을 따로 생성한다
		: 결론적으로는 테이블A 와 mapping 테이블은 1: n 관계 ,테이블B와   mapping 테이블은 1:m 관계가 된다
		: https://siyoon210.tistory.com/26



단방향, 양방향 연관관계
	: https://velog.io/@conatuseus/%EC%97%B0%EA%B4%80%EA%B4%80%EA%B3%84-%EB%A7%A4%ED%95%91-%EA%B8%B0%EC%B4%88-2-%EC%96%91%EB%B0%A9%ED%96%A5-%EC%97%B0%EA%B4%80%EA%B4%80%EA%B3%84%EC%99%80-%EC%97%B0%EA%B4%80%EA%B4%80%EA%B3%84%EC%9D%98-%EC%A3%BC%EC%9D%B8
	: 한쪽에서만 다른 쪽을 접근 할 수 있는지 , 양쪽에서 모두 서로 접근할 수 있는지.
	: 객체의 연관관계 >>   주소(참조)로 관계를 맺고, 항상 단방향이다 ( 양쪽에 모두 서로를 참조하는 필드가 있다해도 정확히 말하면 서로 다른 단방향 관계이다. )
	: 테이블 연관관계 >>  외래키로 관계를 맺고, 외래 키 하나만으로 필요따라 양방향 / 단방향 관계 모두 가능하다.
		: 양방향 >> 부모 엔티티에 @OneToMany 있으면. 즉, 부모 쪽에서도 자식쪽으로의 접근이 가능할 떄. 
		: 단방향 >> 부모 엔티티에 @OneToMany 없으면. 즉, 부모 쪽에서는 자식쪽으로의 접근이 불가할 떄. 

	: ex ) 학생과 학교
		객체 >> 단방향 : Studnet 객체와 School 객체는 단방향 관계이다. Student.school 필드를 통해 학생이 다니는 학교를 알 수 있지만, School 객체에는 student 에 접근하는 필드가 없어 학교에 다니는 학생들을 알 수 없다.

		테이블 >> 양방향 : STUDENT 테이블과 SCHOOL 테이블은 외래키로 연관관계를 맺는다. STUDENT 테이블의 FK 인 SCHOOL_NAME 으로 학생과 학교를 join 할 수 있고, 학교와 학생을 join 할 수 있다.


(연관관계) 주인 ownership >> 양방향 연관관계에서의 관리 주체. 관리자.
	: https://velog.io/@conatuseus/%EC%97%B0%EA%B4%80%EA%B4%80%EA%B3%84-%EB%A7%A4%ED%95%91-%EA%B8%B0%EC%B4%88-1-i3k0xuve9i

	: 연관관계의 주인만이 데이터베이스 연관관계와 매핑되고 외래 키를 관리(등록, 수정, 삭제)할 수 있다. 반면에 주인이 아닌 쪽은 읽기만 할 수 있다.

		영속성 컨텍스트 Persitence Context >> JPA 내부에서 Entity 를 영구저장(영속화)하는 논리적인 환경	
			: DB와 시스템 간의 중개자 역할
			: PK(ID) 를 기반으로 기능한다.
				: 주의 >> 모든 쿼리가 영속화 되는게 아니고, PK 대한 쿼리"만" 영속화 가능하다.
					
			: 장점
				1. 캐싱(1차 캐시) >> 한번 불러왔던건 캐시 데이터로 저장시켜둔다.
					: 매번 db 접근하는게 아니라 영속성 컨텍스트에 캐시된 데이터 중에서 먼저 찾고 없으면 그떄 db 에 접근해 캐시 데이터에 저장하는거라 속도 줄일 수 있다
					: 캐시 데이터로 저장된 엔티티의 상태를 "스냅샷"을 찍어 저장해둔다.
						: 스냅샷 Snapshot
							: 특정 시점 떠 둔 데이터의 사본.
							: 데이터 복원 및 복제 용
							: 백업 != 스냅샷
								: 백업은 원본 데이터를 그대로 복사해 storage 상에 저장해두는거고, 스냅샷은 메타데이터를 복사하는거고 별도이 변경이 있기 전까진 storage 상에 저장해두진 않는다

				2. 쓰기 지연 (트랜젝션 지원)>> 쿼리를 바로 db 로 전송하는게 아니라(수행되는게 아니라) 쓰기지연 저장소에 저장해놨다가 flush( ) 시점에 전송한다
					: 잦은 I/O 발생을 방지한다
					: 캐시 데이터가 저장되는 곳(db서읽어왔던데이터저장) != 쓰기지연저장소(전송될쿼리문저장)

				3. 변경 감지 dirty checking >> 기존 snapshot 과 비교해 얼마나 변경됬는지(더러워졌는지) 자동으로 감지한다
					: persistnect context 는 snapshot 과 entity 룰 비교하여 변경이 감지되면,  자동으로 UPDATE 문을 생성하여 쓰지지연 sql 저장소에 저장한다.

				: 일반적으로는 EntityManager 한 개당 하나의 영속성 컨텍스트를 갖지만, 스프링에서는 공통된 영속성 컨텍스트 하나를 여러 EntityManager가 참조한다

				:  엔티티 인스턴스를 막 생성한 상태.

			2. 영속 managed :  persistence context 에서 관리 중인 상태
				: 비영속 상태의 엔티티 인스턴스를 EntityManager 의 persist(  )메서드를 사용하여 persistence context 에 저장된 상태
					: this.entityManager.persist( 엔티티명 );

				: JPA 를 통해 불러온 데이터는 모두 영속성 컨텍스트의 캐시데이터에 저장시킨다.
					: this.entityManager.find( 키) 사용시 매번 db 접근하는게 아니라 영속성 컨텍스트에 캐시된 데이터 중에서 먼저 찾고 없으면 그떄 db 에 접근해 캐시 데이터에 저장하는거라 속도 줄일 수 있다
					: JPA는 데이터를 저장하기 전 영속성 컨텍스트에 저장된 데이터가 있는지 확인한다. 동일 데이터가 존재하면 update, 없으면 insert를 수행한다

				: transcation 이 시작된 이후 JPA 가 생성한 쿼리들은 바로 실행되지 않고 모두 "쓰기 지연 저장소"에 저장한다. commit 이 수행되어야 생성되었던 쿼리문들을 수행한다.
 

				: flush >> 영속성 컨텍스트의 변경 내용을 db 에 반영하는 절차
					: 플러시 모드 따라서 JPA 가 알아서 flush 시켜주긴 하지만, 직접 this.entityManager.flush( ) 수행으로 직접 flush 수행도 가능하다
					: 플러시 모드
						1. @FlushModeType.AUTO : (select 같은 단순 읽기 제외) 쿼리 실행할 때 플러시 << default
						2. @FlsuhModeType.COMMIT : commit 수행할 떄만 플러시

					: flush( )  VS commit( ) 
						: flush( )   >> 쿼리 전송 역할
							: rollback 가능하다

						: commit( )  >> 내부적으로 flush 를 수행 한 뒤 트랜잭션을 끝내는 역할
							: rollback 불가하다

			3. 준영속 detached : persistence context 에 저장되어 있었으나 분리된 상태
				: 영속 상태의 엔티티를 detach 시키거나 영속성 컨텍스트 자체가 초기화 / 종료되면 컨텍스트 내부의 모든 데이터는 준영속 상태가 된다
					: this.entityManager.detach( 엔티티명 ); //특정 entity detach
					: this.entityManager.close( ); // 영속성 컨텍스트 종료
					: this.entityManager.clear( ); // 영속성 컨텍스트 초기화

				: 관리되지는 않는 상태이지만 JPA의 지원을 받지 못할 뿐, 정상적인 데이터를 갖는 인스턴스이다.

				: 준영속상태의 데이터는 데이터 병합 기능을 사용하여 다시 영속 상태로 돌릴 수 있다
					this.entityManager.merge( 엔티티명 );



			4. 삭제 : persistence context 에서 완전히(db 쪽에서까지 ) 삭제된 상태
				: 영속 상태의 엔티티가 persistence context 와 db 양쪽 모두에서 삭제된 상태
					: this.entityManager,remove( 엔티티명 ) ;

			: null 값을 허용하고 싶지않은 필드 위에 명시한다.

					: @Notnull 은 예외를 쿼리 생성 전에 발생시키고,  @Column(nullable=false) 은 예외를 쿼리 실행 중에 발생시킨다.

			: 사실 Entity 내부의 모든 필드는 column 으로 간주되기 떄문에 생략해도 무방하나 디폴트 값이 아닌 다른 값으로 설정 원하면 명시해야된다.

  						@Column(name = "user_nm")

					(1) true : NULL 도 허용한다<< 디폴트값
					(2) false : NOT NULL 로 설정한다.

					@Column(precision = 10, scale = 2)

JPA 를 활용한 CRUD Create생성 Read조회 Update수정 Delete삭제
	: 기본 셋팅 >> Entity 클래스와 Repsitory 인터페이스(CrudRepository 를 상속받은)를 준비 
	(1)Create 생성
		1. get mapping으로 폼 페이지 반환
			: 해당 페이지의 form 은 post 방식 

		2. post mapping으로 폼 데이터 처리
			(1) DTO 객체를 파라미터로 하여 한꺼번에 받음
			(2) DTO 객체를 바탕으로 엔티티 객체 생성
			(3) repository.save( 생성한엔티티객체 )
			(4) 완료페이지로 리다이렉트 	


	(2) Read 조회
		case1. 특정 record 조회
			(0) "/URL{id}" 로 getmapping
			(1) @PathVariable 등을 이용해 id 를 받고, Model 객체도 파라미터로 받음
			(2) 엔티티타입 변수명 = repository.findById( id ).orElse( null ) ; 으로 특정 record 대한 엔티티 얻음
			(3) model.addAttribute( "변수명" , 변수명 );  
			(4) 모델에 저장한 데이터를 변수명.필드명 으로 사용하는 페이지로 이동

		case2. 전체 record 조회
			(0) getMapping
			(1) Model 객체만 파라미터로 받음
			(2)  List<엔티티타입> 변수명 = (List<엔티티타입>)repository.findAll( ) ; 으로 반환 결과를 리스트로 받음
			(3) model.addAttribute( 변수명 );
			(4) model.addAttribute( "변수명" , 변수명 );  
			(5) 모델에 저장한 데이터를 반복문 과 함께 변수명.필드명 으로 사용하는 페이지로 이동

	(3) Update 수정
		: JPA 에 Update 대한 메서드는 따로 없다. 기존 데이터와 똑같은 id 를 가지는 데이터가 저장(save)되면 , 수정작업이라 간주하고(걍 생각해보면 똑같은 id 가 존재할 순 없잖아) 업데이트해준다.
			: id 를 주고 받고 하는게 매우 중요
			: 변경된 내용으로 새로운 entity 를 만들어서 save 하는게 아니라 , 기존 id 를 기반으로 find 한 entitiy 를 직접 "수정"한 것을 save 해야함을 주의 

		1. "/URL{id}"로 getMapping 으로 수정 페이지 반환
			(1) @PathVariable 등으로 id 를 받고, Model 객체도 파라미터로 받음
			(2) 엔티티타입 변수명 = repository.findById( id ).orElse( null ); 으로 특정 record 대한 데이터를 얻음  
				: 그냥 이동 페이지로 id 만 넘기는게 아닌, 엔티티를 직접 넘기는 것은 일반적으로 수정 페이지의 placehold, default 값으로 기존 입력 사항 나오니까
			(3) model.addAttribute( "변수명", 변수명 );
			(4) 모델에 저장한 데이터를 변수명.필드명 으로 사용하는 페이지로 이동
				: 해당 페이지의 form 은 post 방식이고, hidden 으로 id 를 보낸다
					: post 방식은 URL 뒤에 단순 붙여서 못보내니까 "/URL/{{id}}" 같은건 불가하다
			
		2. postMapping 으로 폼 데이터 처리
			: 내가 시도했던 방법 >>  변경 데이터가 들어오지 않으면 기존 데이터가 유지되긴 해도 entity 의 setter 를 사용하므로 비추천
				(1) form 데이터를 dto 로 받을 순 있어도 entity 로 바로 받진 못하니까 @ModelAttribute 로 dto 받고,  dto 에는 id 필드를 만들어두지 않았으므로 @RequestParam 으로 id 를 별도로 받는다.
				(2) 엔티티타입 변수명 = repository.findById( id ).orElse( null ) ; 으로 해당 객체를 얻어낸다
				(3) if(dto.getXXX( ) != null) 변수명.setXXX( dto.getXXX( )); 로 새로 입력된 데이터 대해서만 수정한다
				(4) repository.save( 변수명 ); 한다 
				(5) 완료 URL 로 redirect


			: 교재 방법1 >> 비추. 변경 데이터가 들어오지 않으면 null 값이 들어감
				(1) form 데이터를 @ModelAttribute dto 로 받음
				(2) dto.toEntity( ) 로 entitiy 화
				(3) 엔티티타입 변수명 = repository.findById( dto.getId(  id) ).orElse( null ) ; 해서 기존 객체 뽑음 << 꼭 해야되나? 바로 save( entity화한거) 하면 안되나?
				(4) (변수명 != null) 이면 repository.save(entity화한거) 한다
				(5) 완료 URL 로 redirect

		*******: 교재 방법2 >> 개추. setter 를 사용하지도 않고 변경 데이터가 들어오지 않으면 기존 데이터 유지
				(1) 엔티티클래스에 patch( 엔티티타입파라미터 ) 선언 
				(2) 엔티티타입 변경데터담은변수 = dto.toEntity( ) 해서 변경데이터 담은 dto 객체를 앞서 구현한 patch 함수의 arg 로 넣을 준비를 함
				(3) 엔티티타입 db데터담은변수 = repository.findById( dto.getId( id ) ).orElse( null ) ; 해서 기존 객체 뽑음
				(4) db데터담은변수.patch( 변경데터담은변수 ) 하여 null 값이 아닌 필드에 대해 수정 반영
				(5) repository.save(db데터담은변수); 해서 update 된 entity 객체를 db에 저장 
					
	(4) delete 삭제 >> 간단하게 해당 id 와 바인딩된 데이터가 존재하는지 찾아보고 , 있으면 respository.deleteById(id);
