스트림 문법
	: 리스트와 같은 자료구조에 저장된 요소를 하나씩 순회하면서 처리하는 코드를 간략화된 표현으로 제공하는 패턴
	: 메서드
		strean ( ) >> List<T> 객체를 기반으로 스트림객체를 생성한다 
		map( a -> b ) >> 스트림객체의 요소 하나 단위로 인자 함수를 적용(하여 수정)한다.
		collect( Collectors.toiList( ) ) >> 스트림 객체를 List 화 한다

	: ex1 ) 원본 리스트의 요소들을 형변환한 취한 것들을 요소로 하는 새로운 리스트 "생성".
		: 원본리스트를 변형하는건아니다
		  List< 타입2 > list2 = list1.stream( ).map(  list1의요소변수명을파라미터로하여작업하는화살표함수 ).collect( Collectors.toiList( ) );  
  			: ex ) List<Article > list2 = list1.stream( ).map( dto -> dto.toEntity( ) ).collect( Collectors.toList ( ) ); 

			: 이는 
				List< 타입2 > list2 = new ArrayList<>();
				for(int i = 0 ; i < list1.size( ) ; i++){
					타입1 변수1= list1.get( i );
					. . .
					( 변수1 을 타입2 화 하는 코드 )
 					. . .
					list2.add( 변수2 );	
						
				}  

			을 간략화한 것과 같다


	: ex2 ) 리스트의 요소 마다 작업 수행
		: 원본리스트를 변형하는건아니다
		list.stream( ).forEach( list의요소변수명을파라미터로하여작업하는화살표함수 );
			: ex ) articleList.stream() .forEach( article -> articleRepository.save( article ) );
				: 근데 솔직히 이것보단 articleRepository.savAll( articleList ); 쓰면 되지 뭘 굳이 이렇게 까지 하냐
			: 이는
				for( int i = 0 ; i < list.size( ) ; i++ ){
					타입 변수명 = list.get( i );
					. . .
					( 변수 가지고 작업하는 코드 )
 					. . .
				}

			를 간략화한 것과 같다

서비스 Service
	: controller 와 repository 사이에 위치하는 계층
	: 비즈니스 로직( 내부적인 처리 .  본질적인 작업 . 보통 db 관련 작업 ) 처리
	: 클라이언트가 손님(요리주문),  (REST) Controller 가 웨이터 (주문전달),  Service가 헤드 쉐프( 메인 요리 ), Repository가 보조쉐프( 재료가져옴 ) , DB 가 창고(재료창고) 라고 보면 된다.

	: 서비스 계층은 db 접근 , 컨트롤러에는 서비스계층의 처리 결과 따른 상태코드 및 데이터 반환을 하게 한다

 	: 서비스 클래스 구현하기
		0. service 패키지 생성
		1. XXXService.java "인터페이스" 생성 및 추상 메서드 선언
			: TIP >>  보통 컨트롤러 메서드 프로토타입의 반환형만 잘 바꿔서 복붙하면 된다. 
				: REST 컨트롤러 메서드의 반환형은 대부분 ResponseEntity<엔티티타입> 일텐데 , 서비스 계층에서 컨트롤러로 반환한다는 건 ( 서버 내부에서 일어나는거지 ) 클라이언트에게 반환하는게 아니므로  값에 굳이 상태까지 붙여가면서 전달 할 필요 없다. 서비스 클래스의 메서드는 "엔티티타입" , List<엔티티타입> 같은 걸로만(날 것의 데이터) 한다. 

		2.  XXXService 인터페이스를 구현하는 XXXServiceImpl.java 클래스 생성 및 @Service 어노테이션 추가
			: 내부적으로 XXXRepsotiory 를 @Autowired 받아 db에 접근하는 코드를 작성한다
			******: 이 서비스 클래스가 자식 엔티티, 즉 FK 를 가지는 엔티티에 대한 서비스 클래스라면 헤딩엔티티의 XXXRepsotiory 뿐 아니라 부모 엔티티의 @@@@Repository 까지 선언 후 @Autowired 해야된다.


	: 주의 >>

			선언해놓은 경우 문제의 발생 과정
				step1. 클라이언트가 name , password 와 같은 데이터 뿐 아니라 (이미 존재하는) id값까지 보낸다
				step2. 컨트롤러는 해당 id 정보까지 포함하여 dto 객첼 생성하고 articleService.create(dto)를 통해 서비스계층에 보낸다
				step3. 서비스 계층에선 이를 기반으로 entity 객체를 생성하여 save 한다. id 필드가 null 이 아닌 dto 를 대상으로 dto.toEntity( ) 되는거라 ( auto increment로 새로운 아이디 값이 적용되는게 아니라 ) create 가 아닌 update 가 되버린다.

	: 트랜잭션 Transaction >> 비즈니스 로직 처리의 단위
		: 모두 성공해야하는 일련의 과정. 
			: 중간에 실패하면 지금까지 진행된 작업은 모두 취소. 원래 상태로 복구. ( rollback )
			: 최종적으로 성공하면 DB 반영.
		
		: 예시 ) A 은행에서 인출해 B은행으로 입금한다고 했을 때 A 은행에서 인출은 되었지만 B은행으로 입금이 되지 않았다.
			: 트랜젝션 적용안한 경우>> A 은행에서 돈만 날아간게 되어버린다. 
			: 트랜젝션을 적용한 경우 >> A 은행에서 인출한 작업을 취소하여 처음 상태 그대로다



		: @Transactional 
			: 트랜잭션으로 관리하고 싶은 대상, 그러니까 트랜잭션으로 묶어 일련의 과정으로 처리하고 싶은 대상 위에 명시하면 트랜잭션으로 관리할 수 있다
				: 보통 트랜잭션은 서비스 클래스 자체의 윗부분 || 서비스 클래스 내의 메서드 위에 쓰인다
					: 서비스 클래스에서 CRUD 하고, orElseThrow 같은걸로 exception 발생시킬 수 있으니까
					: 서비스 클래스 자체의 윗 부분에 명시하면 해당 서비스 클래스 내의 모든 메서드에 대해 @Transactional 이 적용된다.
