H2 데이터베이스 : 현재 사용하는 주 db가 있더라도, ㅈㄴ 편하므로 꼭 익혀라
	: 종류
		(1) Server Mode : 여느 db들( mySQL , .. ) 처럼 사용
			: H2 실행 파일을 다운로드 필요.
			: 데이터가 로컬에 저장된다.
			:  application.properties에 H2 DB 주소 기입 및 환경 설정
			:  (애플리케이션 외부에서) 터미널로 H2 DB 를 실행시킨 후 사용 가능


		(2) Embedded Mode : 여러모로 편함.
			: 파일 다운 필요 없고,  build.gradle 로 설정만 함.
				: In-Memory 로 하든 Embeded 로 하든 똑같이 
					1. runtimeOnly 'com.h2database:h2'  
					2. implementation 'org.springframework.boot:spring-boot-starter-jdbc'

			: 애플리케이션을 실행/종료와 함께 실행/종료되고, 데이터가 로컬에 저장된다.
			:  application.properties에 H2 환경 설정
			   : spring.datasource.url 에  "mem" 키워드가 포함이 안되어있고, DB 데이터가 저장될 경로를 입력해야된다. 이외엔 모두 Embeded Mode 와 동일함.
				: DB데이터저장될경로 >> 해당 경로에 폴더가 새로 생기고( 이미 있다면 그냥 그거 쓰고 ), 거기에 데이터 저장된다. 해당 파일을 직접 삭제하지 않는 이상 데이터는 유지된다.
					:  . /경로 >> 현재 "작업" 디렉토리의 하위에 저장
						: ex ) 현재 C:/backend/jpa1 디렉터리에서 작업 중이고, "./h2db/data" 로 설정 하면 -->  C:/backend/jpa1/h2db/data 에 생성됨

					: ~/경로 >> 현재 "사용자" 디렉토리의 하위에 저장.
						: ex ) 현재 사용자 디렉터리가  C:/users/jiyu 이고, "~/h2db/data" 로 설정 하면 -->   C:/users/jiyu/h2db/data 에 생성됨

				spring.h2.console.enabled=true
				spring.h2.console.path=/h2-console
				spring.datasource.driver-class-name=org.h2.Driver
				spring.datasource.url=jdbc:h2:{DB데이터저장될경로}
				spring.datasource.username={사용자명}
				spring.datasource.password={비번}

			: db 접속 방법 >> localhost:{포트}/h2-console 에 접속 후, Driver Class, JDBC URL, User Name, Password를 application.properties 에 설정했던 대로 입력 한다.


		(3) In-Memory Mode : 데이터베이스가 일회성으로 필요한 경우에 유용
			: 파일 다운 필요 없고,  build.gradle 로 설정만 함.
			:  애플리케이션을 실행/종료와 함께 실행/종료되고,  데이터가 애플리케이션의 "메모리"에만 잠깐 저장됨. 즉, 서버를 재시작하면 데이터가 삭제됨.	
			:  application.properties에 H2 환경 설정하여 사용
			   : spring.datasource.url 에 들어간  "mem" 키워드로 유추 할 수 있듯 memory 를 사용하고, DB의 이름을 기입함. 이외엔 모두 Embeded Mode 와 동일함.
				spring.h2.console.enabled=true
				spring.h2.console.path=/h2-console
				spring.datasource.driver-class-name=org.h2.Driver
				spring.datasource.url=jdbc:h2:mem:{DB명}
				spring.datasource.username={사용자명}
				spring.datasource.password={비번}

			: db 접속 방법 >>Embedded Mode와 같다.

Native SQL Query : 특정 db에 종속적인 sql 쿼리. 일반적인 SQL 문

JPQL Java Persistence Query Language : 객체지향 쿼리 언어(엔티티중심의쿼리언어) 표준 스펙.명세. (실제로 구현된 것은 아님)
	: SQL 문을 추상화 한 것.
	: JPA 제공 메서드 만으로는 불가능한 복잡한 쿼리문을 날리고 싶을 때 사용한다
	: tip >> SQL 과는 다르게 "테이블"이 아닌 "엔티티"를 중심으로 쿼리한다. 
		: SQL문을 나타내는 문자열에 등장하는 얘들은 테이블명, 컬럼명 .. 그런거다
		: JPQL문을 나타내는 문자열에 등장하는 얘들은 엔티티명, 필드명 .. 그런거다
	: 사용 절차
		step1. 쿼리객체 생성 >> TypedQuery<반환타입> query =  em.createQuery( JPQL문, 반환타입명.class ); 
		step2. 생성한 쿼리객체를 대상으로 getResultList( ) 호출 >> List<반환타입> 결과변수 = query.getResultList( );
			: getSingleResult( ) 이란 것 도 있는데, 대부분 getResultList( ) 를 쓰는 편이다 >>
				: getResultList 의 경우 결과가 몇개이든(0 개이든 1개이든 100개이든) List 타입으로 반환해준다. 그러니까 다양한 갯수의 결과를 받을 수 있다.
				: getSingleResult( ) 의 경우 "반드시" "딱" 1개의 결과만 받아야된다. 0개를 받아도 예외( javax.persistence.NoResultException)를 발생시킨다.

	: 주의 >> 일반적인 SQL 문과는 다르게 JPQL 은 대소문자를 구분한다.
	: 참고 >> JPQL 이 SQL 과 유사하긴 하지만, oracle , mySQL 벤더 간의 문법이 쬐끔씩만 차이 나는것에비하면 JPQL 은 일반적인 SQL 문과 꽤나 다르다 ( HQL 에는 '*' 표현자체가 없다 ) 


HQL Hibernate Query Language : Hibernate 에서 사용하는, JPQL에 맞춘 ,  "객체 지향" 쿼리 언어
	: JPQL 을 구현한 것이 HQL 이라고 봄 된다.



QueryDSL >> HQL 쿼리를 (직접 HQL 문을 작성할 필요 없이) 코드로 HQL 문을 구현할 수 있게 해주고 ,  정적타입(static type)을 이용하는  프레임워크
	: (정적타입을 사용하기 때문에) QueryDSL 은 타입에 안전하다.
	: 복잡한 쿼리나 동적 쿼리 작성이 편리
	: ex ) 
		HQL 로는 다음과 같이 문자열로 직접 써야되는 걸
String username = "java";
String jpql = "select m from Member m where m.username = :username"; // 문자열 형식의 HQL 문
List<Member> result = em.createQuery(query, Member.class).getResultList();
		QueryDSL 로는 다음과 같이 코드로 쓸 수 있다 
String username = "java";
List<Member> result = queryFactory
        .select(member)
        .from(member)
        .where(usernameEq(username))
        .fetch();

트랜잭션 transaction :  DB 상태를 변경하기 위해 수행하는 작업 단위
	: https://mommoo.tistory.com/62
	: transaction은 쿼리문 딱 한 문장이 아니라, 개발자가 정하기 나름
	: 하나의 작업을 안전하게 처리하도록 보장해준다.
	: commit 과 rollback >> 작업 정상적으로 수행 완료시 commit, 아닐 시 rollback
		commit : 작업 결과 반영
		rollback :  작업 수행 이전으로 되돌림

	: 특징 ACID
		(1) 원자성 Atomicity :  마치 한 덩어리인 듯 완전히 반영되거나, 아예 반영이 안된다.
		(2) 일관성 Consistency: 트랜잭션 진행 중 데이터베이스가 변경되더라도 업데이트된 데이터베이스로 트랜잭션이 진행되는것이 아니라, 처음에 트랜잭션 시작 당시 참조한 데이터베이스로, 일관되게, 진행된다. 
		(3) 독립성 Isolation :  하나의 특정 트랜잭션이 완료될때까지, 다른 트랜잭션이 특정 트랜잭션의 결과를 참조할 수 없다. 둘 이상의 트랜잭션이 동시에 실행되고 있더라도 다른 트랜잭션의 연산에 끼어들 수 없다
		(4) 지속성 Durablity : 트랜잭션이 성공적으로 완료됬을 경우, 결과는 영구적으로 반영된다. commit 이후 애플리케이션 오류가 났더라도, db에 커밋된 내용은 잘 반영되어있어야된다.

	: 트랜잭션은 비즈니스 핵심 기능이라기 보다는 부가 기능에 속한다. 
		:  프록시로 자주 만들어진다

프록시 Proxy :  (클라이언트와 타겟 사이에서) 마치 자신이 타겟인 것처럼 요청을 받고, 그 요청을 타겟에게 위임하는 객체. 대리인.
	: 주로 기능 확장 (Decorator pattern) 하거나, 접근 제어 (Proxy pattern)하기 위해 사용
	: 프록시 객체의 조건 >> 클라이언트가 타겟에 요청을 한건지, 프록시에게 요청을 한 것인지 알 수 없어야된다.
		: 타겟와 프록시는 같은 인터페이스를 사용해야됨	
			: 결국은 클라이언트의 코드를 하나도 건들이지 않고, 프록시 추가와 런타임 객체 의존 관계 주입만 변경해서 사용할 수 있게 하는게 목표.
			: 그러니까 클라이언트가 타겟에 요청을 한다는건, 클라이언트의 코드는 그 타겟의 인터페이스에 의존적인 코드란 것. 따라서 클라이언트의 요청을 프록시가 타겟처럼 문제없이 받기위해선 (타겟 뿐 아니라 ) 프록시도 타겟 인터페이스의 구현체여야된다. 

	: 프록시가 꼭 바로 타겟에게 요청을 위임하는게 아니라, 또 다른 프록시에게 요청을 위임하고 다른 프록시가 타겟에게 요청을 위임하게 할 수도 있다
		 

프록시 패턴과 데코레이터 패턴 : 모두 프록시를 사용하는 패턴인데, 의도에 따라 구분된다.
	: https://kghworks.tistory.com/161
	: https://velog.io/@codemcd/%EB%94%94%EC%9E%90%EC%9D%B8-%ED%8C%A8%ED%84%B4-%ED%94%84%EB%A1%9D%EC%8B%9C-%ED%8C%A8%ED%84%B4%EB%8D%B0%EC%BD%94%EB%A0%88%EC%9D%B4%ED%84%B0-%ED%8C%A8%ED%84%B4
	데코레이터 패턴 (Decorator pattern) :  부가기능 추가 목적의 패턴
		: 부가기능 추가 목적으로 작성된 각 프록시를 데코레이터라고 한다
		: 구현 >> 데코레이터 코드들은 뿔뿔이 작성되어있고, 클라이언트의 코드에선 각 데코레이터 코드를 조합해 요청하는 꼴로 쓰인다
			: 데코레이터 코드 >> 타겟 코드와 같은 인터페이스를 구현하지만, 내부적으로 부가적 기능(추가적인 메서드)을 포함하고, 타겟 객체를 "받을 수 있는" 필드가 정의되어 있어 "외부에서"(데코레이터 코드 내부적으로 타겟 객체를 생성하는게 아님) 해당 필드에 할당된 객체를 통해 타겟의 기능을 수행할 수 있다. 
			: 클라이언트 코드 >> 
				step1. 타겟 객체 와 특정데코레이터 객체 를 (둘 다) 생성하는데, 데코레이터 객체를 생성할 때 타겟 객체를 감싸는 꼴로 생성한다. ( 생성자 arg 로 넣어 해당 데코레이터 객체의 필드로 활용 가능하게 한다). 
				step2. 생성한 (타겟 객체가 아닌) 데코레이터 객체를 활용한다

		: 컴파일 시점에는 다양한 데코레이터들이 존재할 수 있지만, 어떤 데코레이터가 실제로 사용될지는 하드코딩되어있지 않다(미리 결정되있지 않다). 결국 클라이언트의 요청에 따라 동적으로 데코레이터를 조합하여 사용할 수 있다.
			

		: 대표사례 
			(1) java.io.InputStream / OutputStream 




	프록시 패턴 (Proxy pattern) : 클라이언트 접근 방식 제어 목적의 패턴
		:  클라이언트가 실제로 객체를 생성하지 않더라도, 프록시를 통해 객체의 참조를 관리할 수 있게된다
			: 그러니까 프록시 패턴은 결국 추상화를 하는 방법 중 하나인 것이다. 
		: 구현 >> 클라이언트 코드에서 프록시 객체만 생성 및 사용하여 타겟 객체의 기능을 수행한다. 프록시 객체 코드 내부에선 프록시 객체의 메서드가 호출될 때, 타겟 객체를 생성하고 해당 객체를 사용한다.
 			: 프록시 코드 >> 타겟 코드와 같은 인터페이스를 구현하고, 타겟 객체를 "받을 수 있는" 필드가 정의되어 있어 해당 필드에 할당된 객체를 통해 타겟의 기능을 수행할 수 있게 한다. 데코레이터 코드와는 다르게 외부에서 타겟 객체를 주입 받는 형태가 아니라, 메서드 내부에서 생성시키게 되어있어 해당 메서드가 호출될 때 "내부에서" 타겟 객체를 "생성"하게 하고, 해당 타겟 객체를 사용해 작업을 하게 된다. 그리고 특별한 부가적인 기능을 하는 메서드를 정의하진 않고(부가적 기능 추가하는건 데코레이터의 목적) 타겟 코드에 정의된 메서드와 유사하게 구성한다.
 			: 클라이언트 코드 >> (타겟객체를 따로 x) 프록시 객체만 생성하고, 생성한 프록시 객체로 타겟 객체의 기능을 수행한다.

		: remote object 에 유용하다.
		: 타깃을 특정 레이어에서 write -> read-only로 수정하고 싶을 때 유용하다.
		: 대표사례 
			(1) JPA의 lazy loading 시 참조하게 되는 프록시 객체 : target 의 참조가 일어나기 전까지 실제로 db 에서 쿼리문을 실행시키지 않는다.
			(2) java.util.Collections.unmodifiableCollection() : Collection에 대한 프락시를 만들어 wirte 메서드 호출 시 UnsupportedOperationException를 발생시킨다.


다이내믹 프록시 Dynamic proxy : 특정 타겟에 종속적이지 않은 프록시 기법
	:  개발자가 프록시 객체를 코드로 구현하여 정적인 시점(컴파일 시점)에서 생성하는 것이 아닌(하드코딩해두는게 아닌), 설정과 필요한 로직만 구현하고 런타임 시점에 프록시 객체를 자동으로 생성하게 하는 것.
	: 정적인 프록시 생성의 단점을 보완하기 위해 등장
		:  각 정적 프록시 코드는 특정 타겟에 한정적이다. 같은 기능을 담더라도 타겟이 다르다면 프록시 객체를 각각 만들어줘야된다는 단점이 있다. >> 프록시를 도입했음에도 코드 중복으로 비효율적이고, 유지보수 어렵다
			: ex ) 타겟이 animal , person 이고 둘다 ( animal 객체와 person 객체를 ) save 하는 공통된 기능이 있더라도, animal 과 person 각각에 대한 프록시 객체를 만들어줘야된다. 
		: 이와 다르게 다이나믹 프록시의 경우 좀더 기능 중심적이면서 특정 타겟에 종속적이지 않은 코드로, 다양한 타겟 객체를 대상으로 작동 가능하게 해준다. 

	: 자바에서 대표적인 동적 프록시 기술 종류
		(1) JDK 동적 프록시 >> 인터페이스만을 기반으로 프록시 객체 생성 가능
			: https://gong-story.tistory.com/22
			: java.lang.reflect (리플렉션 패키지) 를 활용한다.
			: newProxyInstance( 특정타겟의클래스로더 , 특정타겟이구현해야될인터페이스목록, 특정타겟과바인딩될핸들러 ) >> 특정 타겟에 대한 프록시 객체를 생성 시킴
				: 클래스로더 대상으론 "인터페이스만" 가능함 주의 !!!! (일반 클래스 타입은 불가)

			: InvocationHandler >> 특정 타겟에 대한 특정 프록시 객체의 매서드 호출 시 실행될 콜백함수를 바인딩시켜줄 핸들러에 대한 인터페이스
				:  private final Object target 필드 >> 타겟 객체를 저장
					: InvocationHanlder 구현 객체 생성할 때, 생성자의 arg 로 대입하게 되어있다.
				: invoke( 특정프록시객체, 호출한메서드정보, 호출한메서드에전달된파라미터) 메서드 >>  프록시객체의 메서드가 호출되었을때, 대신 실행되는 InvocationHandler 구현체 내부에 정의된 메서드
					: 개발자가 직접 invoke( ) 를 호출하는게 아니라, 이벤트 핸들러와 바인딩된 프록시 객체의 메서드 호출 시 자동으로 invoke( ) 까지 실행시켜주는거다.
				: newProxyInstance( ... , ... , ... )  의 3번쨰 arg 로 들어가게 된다

		

			: 사용 절차
				1.  java.lang.reflect.InvocationHandler 인터페이스를 구현한 핸들러 선언
				2.  클라이언트 코드에서
					(1) 타겟 객체 생성
					(2) 생성한 타겟 객체를 arg 로 하여 핸들러 객체 생성
					(3) 생성한 핸들러 객체를 arg 로 하여 newProxyInstance 메서드로 프록시 객체 생성
					(4) 해당 프록시 객체로 프록시 객체의 메서드 호출


		(2) CGLIB Code Generator Library  : 클래스 기반 & 바이트 코드 기반으로 프록시 객체 생성
			: https://gong-story.tistory.com/23?category=975421
			: 바이트코드를 조작하여 프록시 클래스를 생성해주기 때문에 동적 프록시보다 성능적으로도 좋다
			: MethodInterceptor >> Callback 이라는 인터페이스를 상속 받으면서, 특정 타겟에 대한 특정 프록시 객체의 매서드 호출 시 실행될 콜백함수를 바인딩시켜줄 인터페이스		
				: JDK 동적 프록시의 InvocationHandler 와 역할이 비슷
				:  intercept(  타겟객체 , 호출한메서드정보, 호출한메서드에전달된파라미터, 메서드호출에사용, MethodProxy 객체  )  메서드 >> 프록시객체의 메서드가 호출되었을때, 대신 실행되는 MethodInterceptor 구현체 내부에 정의된 메서드
					: MethodProxy 객체 >> 프록시 객체를 나타낸다.
					: InvocationHandler 와는 다르게 첫 arg 가 프록시 객체가 아니라, 마지막 arg 가 프록시객체임을 헷갈리지 x.
					: 개발자가 직접 intercept 를 실행시킨다는게 아니라, 해당 타겟에 대한 프록시 객체의 메서드 실행시 자동적으로 실행되는거다.


				
			: Enhancer 클래스 >> Proxy 객체를 생성할 수 있는 클래스
				: new Enhancer( ) 로 구해진 객체를 대상으로 proxy 객체를 얻을 수 있다.
				: Enhancer 타입으로 생성된 Proxcy 객체를 대상으로 .setSuperClass( 특정클ㄹ스명.class )  , .setCallback( MethodInterceptor 구현객체  ) , create( ) 을 사용 가능하다 .
					: .setSuperClass( 특정클래스명.class ) >> 어떤 클래스를 "상속"받을지 지정
					: .setCallback( MethodInterceptor 구현객체 ) >>프록시에서 실행할 로직 지정
					: .create( ) >> 설정된 내용( 상속할 클래스, 바인딩될 콜백함수 ) 을 바탕으로 프록시 객체 생성



			: 사용 절차
				1. MethodInterceptor 를 구현하는 클래스 정의
				2. 타겟 객체 생성
				3. Enhancer 객체 생성
				4. 생성한 Enhancer 객체를 대상으로, 생성한 타겟 객체를 arg 로 하여 setSuper 를 적용
				5. 생성한 Enhancer 객체를 대상으로, MethodInterceptor 구현 객체를 arg 로 하여 setCallback 적용
				6. 생성한 Enhancer 객체를 대상으로, create 를 적용하여 프록시 객체 구함
				7. 생성한 프록시 객체를 대상으로 프록시 객체의 메서드 호출




	: spring proxyFactory >> JDK 동적 프록시/CGLIB를 추상화해 사용해 편리하게 사용하게 해놓은 것.

관점 지향 프로그래밍 AOP Aspect Oriented Programming >> 애플리케이션을 횡단 관심사 관점으로 보는 것.	 
	: 애플리케이션 내 로직을 크게 구분하면
		(1) 핵심 기능: 해당 객체가 제공하는 고유의 기능
		(2) 부가 기능 : 핵심 기능을 보조하기 위해 제공되는 기능 ( ex: 로그 추적 기능, 트랜잭션 기능 )
			: 부가 기능을 횡단 관심사(cross-cutting concerns) 라고도 한다

	: 애플리케이션 내 여러 로직에 중복되는 부가 기능이 있고, 그걸 직접 코드로 집어넣으면 유지보수가 어려워진다. 이를 해결하기 위한것이 AOP 다 

	:  AOP 는  부가 기능을 핵심 기능에서 분리해 한 곳으로 관리하도록 하고, 이 부가 기능을 어디에 적용할지 선택하는 기능을 합한 하나의 모듈

	: 용어
		(1) Aspect : 비즈니스 로직에 대한 트랜잭션 처리 모듈 (보통 싱글톤으로 관리)
		(2) Advice : 비즈니스 로직 앞/뒤로 존재하는 트랜잭션 기능 (e.g. 트랜잭션 시작, 커밋, 롤백 등)
		(3) Pointcut : 트랜잭션 처리 모듈을 적용해야 하는 비즈니스로직 선별 알고리즘 (회원 가입, 송금, 등을 선별)
		(4) Joinpoint : 어드바이스 적용 위치

	: EntityManagerFactory 로 생성 가능하고, 스레드 단위로 생성하는게 지향된다.

	: 내부에 데이터 소스(db커넥션)를 유지하면서 db와 통신함. 가상의 db라고 봐도 무방.
	: 사용이 끝난 엔티티 매니저는 반드시 종료( .close( ) )시켜줘야된다

		sol1. spring data jpa && 스프링부트 사용 :  @PersistenceContext를 통해 스프링빈을 DI 받아 씀.	
			: https://sjh9708.tistory.com/60
			: application.properties에 기입된 정보를 토대로 EntityManagerFactory가 생성됨
			: EntityManager는 thread-safe 하지 않기 떄문에, 싱글톤관리하여 다른 스레드들끼리 같은 EntityManager 를 공유하면 동시성 문제가 생길 수 도 있다. 따라서 EntityManager 는 스레드 별로 생성되어야한다. 
				: @Autowired 로 EntityManager를 DI 받으면 안된다. 일반적으로 @Autowired 를 하면 별다른 설정없으면 싱글톤관리되는 빈을 주입해주기 때문이다.
					: 근데 스프링부트 특정 버전 부터는 @Autowired 를 대신 써도 문제가 없게 되었다고 하긴 했는데, 여전히 @Autowired 가 아닌 @PersistenceContext 의 사용이 더 지향되는 추세이다.

				: https://velog.io/@biddan606/EntityManager%EB%A5%BC-%EC%A3%BC%EC%9E%85%ED%95%A0-%EB%95%8C-Autowired-vs-PersistContext
			: @PersistenceContext 는 빈을 DI 시켜준다는 점에서 @Autowired 와 비슷하지만, 싱글톤으로 관리되냐의 여부가 다르다
			: @PersistenceContext 의 작동 방식
			    : SharedEntityManagerCreator 로  "싱글톤" "EntityManager 프록시 객체"를 생성.
			    : TransactionSynchronizationManager 로 "EntityManager 프록시 객체" 활용시 트랜잭션마다 별도의 "EntityManager" 를 생성 및 관리.

				1. @PersistenceContext 명시
				2. EntityManagerFactory 빈이 있는지 검사하고 있으면 get , 없으면 새로 생성
				3. SharedEntityManagerCreator 메서드를 통해, 앞서 구한 EntityManagerFactory 객체를 기반으로 "트랜잭션과 동기화된 공유 EntityManager 프록시"를 "싱글톤으로" 생성하고 이를 반환함
					: 즉, 트랜잭션의 시작과 종료에 따라 자동으로 열리고 닫히거나||플러시되는 , EntityManager 를 추상화해 쉽게 사용할 수 있게 만들어진 객체(== EntityManager 프록시 객체)가 생성된다.
					: 헷갈리지 말아야할 것은 , 싱글톤인건 "EntityManager 프록시 객체"이지, "EntityManager 객체"가 싱글톤인건 아니다.
						: 그리고 프록시 객체에서 타겟 객체는 애초에 생성되있는게 아니라 호출되면 그제서야 만드는 것을 잊음 안된다. EntityManager 프록시 객체 생성된 시점에, EntityManager 객체도 함꼐 생성되는게 아니다.
						: "EntityManager 프록시 객체" 자체는 싱글톤이어도 문제 없는건, 걔는 걍 껍데기일 뿐이고 실질적인 트랜잭션 별 EntityManager에 대한 처리는 TransactionSynchronizationManager 에서 따로 해주기 떄문이다. 

				4.  "EntityManager 프록시" 를 빈으로 주입해준다
				5. 해당 EntityManager 프록시 빈을 대상으로 EntityManager 의 메서드를 호출하면
					(1) 프록시는 현재 스레드의 "트랜잭션 컨텍스트"(persistence context 가 아님)를 확인 및  EntityManager 객체를 구한다 : TransactionSynchronizationManager 를 사용해 현재 트랜잭션과 연관된 EntityManager 객체가 이미 생성되있는지 확인한다
						: 만약 현재 트랜잭션과 연관된 EnityManger 가 이미 있으면 별도 생성없이 그거 그대로 쓰고, 없으면 EntityManagerFactory를 사용해 EnityManager 객체를 새로 생성 및 현재 트랜잭션 컨텍스트에 바인딩한다. 
					(2)  EntityManager 프록시 객체가 내부적으로 구한 EntityManager 객체를 활용해 작업처리한다
					(3) 트랜잭션 종료시 , TransactionSynchronizationManager 를 통해 바인딩된 EntityManager를 플러시하고 닫는다.

				: 서비스 클래스의 메서드 마다 생성.
				EntityTransaction et = em.getTransaction( );

			step2. 트랜잭션 시작 , 종료( 커밋||롤백 )
				: 엔티티트랜젝션객체가 생성된 서비스 클래스의 메서드 내부 이후라인의 "try-catch"문에서 진행
				: try 문 시작부분서 .begin( ) 으로 트랜잭션 시작
				: try 문 중간부분서 비즈니스로직수행
				: try 문의 "마지막"에 .commit( ) 을 작성하여, 비즈니스 로직 실행 중 예외가 발생하지 않았다면 이를 db에 반영함
				: catch 문에 .rollback( ) 하여, 비즈니스 로직 실행 중 예외가 발생했다면 이를 없던일로 침. db에 반영 안함.

				try{		
					et.begin( ); //트랜잭션 시작
					. . . 비즈니스 로직 실행 . . .		
					et.commit( ); //무사히 마쳤음 커밋
				}catch (Exception e){
					et.rollback(); // 비즈니스 로직 수행 중 예외 발생 시 트랜잭션 롤백
					. . .
				}finally{
					em.close( ); // 엔티티매니져 종료
					}
				emf.close( ); // 엔티티매니저팩토리 종료







JPA 가 제공하는 어노테이션
    : (객체와 테이블간의) 매핑정보 설정 관련
	(0) @Entity : 해당 클래스를 엔티티, 즉 테이블에 매핑될 대상으로 정의. 
		: 필수적
		: 테이블과 매핑시킬 클래스명 위에 명시. 
		: @Entity가 적용된 클래스를 "엔티티"라고 한다

	(1) @Table : 엔티티에 매핑될 테이블의 구체적 정보 설정
		: 필수 아님
		: 속성
		    1. name : 테이블명 설정
			: 미설정시 디폴트로 클래스명 자체가 테이블명이 됨.

	(2) @Id : 엔티티의 필드를 테이블의 PK 에 매핑
		: 엔티티클래스의 대표 필드 위에 명시. 
		: @Id 가 적용된 필드를 식별자 필드라고 한다

	(3) @Column : 필드에 매핑될 컬럼의 구체적 정보 설정
		: 필수 아님
		: 속성
		    1. name : 컬럼명 설정
			: 미설정시 디폴트로 필드명이 컬럼명이된다.

    : 엔티티매니저 관련
	@PersistenceUnit : entityManagerFactory를 주입시켜준다.
	@PersistenceContext : entityManager를 주입시켜준다.

    : 트랜잭션 관련
	@Transactional : 해당 메서드를 트랜잭션 처리해준다.

H2 데이터베이스 : 현재 사용하는 주 db가 있더라도, ㅈㄴ 편하므로 꼭 익혀라
	: 종류
		(1) Server Mode : 여느 db들( mySQL , .. ) 처럼 사용
			: H2 실행 파일을 다운로드 필요.
			: 데이터가 로컬에 저장된다.
			:  application.properties에 H2 DB 주소 기입 및 환경 설정
			:  (애플리케이션 외부에서) 터미널로 H2 DB 를 실행시킨 후 사용 가능


		(2) Embedded Mode : 여러모로 편함.
			: 파일 다운 필요 없고,  build.gradle 로 설정만 함.
				: In-Memory 로 하든 Embeded 로 하든 똑같이 
					1. runtimeOnly 'com.h2database:h2'  
					2. implementation 'org.springframework.boot:spring-boot-starter-jdbc'

			: 애플리케이션을 실행/종료와 함께 실행/종료되고, 데이터가 로컬에 저장된다.
			:  application.properties에 H2 환경 설정
			   : spring.datasource.url 에  "mem" 키워드가 포함이 안되어있고, DB 데이터가 저장될 경로를 입력해야된다. 이외엔 모두 Embeded Mode 와 동일함.
				: DB데이터저장될경로 >> 해당 경로에 폴더가 새로 생기고( 이미 있다면 그냥 그거 쓰고 ), 거기에 데이터 저장된다. 해당 파일을 직접 삭제하지 않는 이상 데이터는 유지된다.
					:  . /경로 >> 현재 "작업" 디렉토리의 하위에 저장
						: ex ) 현재 C:/backend/jpa1 디렉터리에서 작업 중이고, "./h2db/data" 로 설정 하면 -->  C:/backend/jpa1/h2db/data 에 생성됨

					: ~/경로 >> 현재 "사용자" 디렉토리의 하위에 저장.
						: ex ) 현재 사용자 디렉터리가  C:/users/jiyu 이고, "~/h2db/data" 로 설정 하면 -->   C:/users/jiyu/h2db/data 에 생성됨

				spring.h2.console.enabled=true
				spring.h2.console.path=/h2-console
				spring.datasource.driver-class-name=org.h2.Driver
				spring.datasource.url=jdbc:h2:{DB데이터저장될경로}
				spring.datasource.username={사용자명}
				spring.datasource.password={비번}

			: db 접속 방법 >> localhost:{포트}/h2-console 에 접속 후, Driver Class, JDBC URL, User Name, Password를 application.properties 에 설정했던 대로 입력 한다.


		(3) In-Memory Mode : 데이터베이스가 일회성으로 필요한 경우에 유용
			: 파일 다운 필요 없고,  build.gradle 로 설정만 함.
			:  애플리케이션을 실행/종료와 함께 실행/종료되고,  데이터가 애플리케이션의 "메모리"에만 잠깐 저장됨. 즉, 서버를 재시작하면 데이터가 삭제됨.	
			:  application.properties에 H2 환경 설정하여 사용
			   : spring.datasource.url 에 들어간  "mem" 키워드로 유추 할 수 있듯 memory 를 사용하고, DB의 이름을 기입함. 이외엔 모두 Embeded Mode 와 동일함.
				spring.h2.console.enabled=true
				spring.h2.console.path=/h2-console
				spring.datasource.driver-class-name=org.h2.Driver
				spring.datasource.url=jdbc:h2:mem:{DB명}
				spring.datasource.username={사용자명}
				spring.datasource.password={비번}

			: db 접속 방법 >>Embedded Mode와 같다.

트랜잭션 transaction :  DB 상태를 변경하기 위해 수행하는 작업 단위
	: https://mommoo.tistory.com/62
	: transaction은 쿼리문 딱 한 문장이 아니라, 개발자가 정하기 나름
	: 하나의 작업을 안전하게 처리하도록 보장해준다.
	: commit 과 rollback >> 작업 정상적으로 수행 완료시 commit, 아닐 시 rollback
		commit : 작업 결과 반영
		rollback :  작업 수행 이전으로 되돌림

	: 특징 ACID
		(1) 원자성 Atomicity :  마치 한 덩어리인 듯 완전히 반영되거나, 아예 반영이 안된다.
		(2) 일관성 Consistency: 트랜잭션 진행 중 데이터베이스가 변경되더라도 업데이트된 데이터베이스로 트랜잭션이 진행되는것이 아니라, 처음에 트랜잭션 시작 당시 참조한 데이터베이스로, 일관되게, 진행된다. 
		(3) 독립성 Isolation :  하나의 특정 트랜잭션이 완료될때까지, 다른 트랜잭션이 특정 트랜잭션의 결과를 참조할 수 없다. 둘 이상의 트랜잭션이 동시에 실행되고 있더라도 다른 트랜잭션의 연산에 끼어들 수 없다
		(4) 지속성 Durablity : 트랜잭션이 성공적으로 완료됬을 경우, 결과는 영구적으로 반영된다. commit 이후 애플리케이션 오류가 났더라도, db에 커밋된 내용은 잘 반영되어있어야된다.

	: 트랜잭션과 동기화된 == 트랜잭션의 시작과 종료에 따라 자동으로 열리고, 닫히거나||플러시 되는 것.

관점 지향 프로그래밍 AOP Aspect Oriented Programming >> 애플리케이션을 횡단 관심사 관점으로 보는 것.
	: 애플리케이션 내 로직을 크게 구분하면
		(1) 핵심 기능: 해당 객체가 제공하는 고유의 기능
		(2) 부가 기능 : 핵심 기능을 보조하기 위해 제공되는 기능 ( ex: 로그 추적 기능, 트랜잭션 기능 )
			: 부가 기능을 횡단 관심사(cross-cutting concerns) 라고도 한다

	: 애플리케이션 내 여러 로직에 중복되는 부가 기능이 있고, 그걸 직접 코드로 집어넣으면 유지보수가 어려워진다. 이를 해결하기 위한것이 AOP 다 

	:  AOP 는  부가 기능을 핵심 기능에서 분리해 한 곳으로 관리하도록 하고, 이 부가 기능을 어디에 적용할지 선택하는 기능을 합한 하나의 모듈

	: 용어
		(1) Aspect : 비즈니스 로직에 대한 트랜잭션 처리 모듈 (보통 싱글톤으로 관리)
		(2) Advice : 비즈니스 로직 앞/뒤로 존재하는 트랜잭션 기능 (e.g. 트랜잭션 시작, 커밋, 롤백 등)
		(3) Pointcut : 트랜잭션 처리 모듈을 적용해야 하는 비즈니스로직 선별 알고리즘 (회원 가입, 송금, 등을 선별)
		(4) Joinpoint : 어드바이스 적용 위치

    : Dynamic proxy : 동적인 프락시 
    : Factory bean : 빈으로 등록

		: 속성 
		    1. strategy : 자동 생성 전략 설정. 어떤 DBMS 기준으로 자동 생성할 건지.
			(1) GenerationType.AUTO >> 하이버네이트가  hibernate.dialect에 설정된 DB 방언 종류에 따라 알아서 매치시켜줌
				: 비추가 되는 건 , 버전 별로 다를 수 있기 때문에 직접 설정하는게 명확하다고 한다. AUTO는 좀 못미덥다.
		******(2) GenerationType.IDENTITY  >>  기본 키 생성을 데이터베이스에 위임
				: 주로 MySQL, PostgreSQL, SQL Server, DB2에서 사용	
				: em.persist( )로 객체를 영속화 시키는 시점에 곧바로 insert 쿼리가 DB로 전송되고, 거기서 반환받은 식별자 값을 가지고 1차 캐시에 엔티티를 등록시켜 관리
					: 이 전략을 사용할 시, MySQL 의 경우 AUTO_INCREMENT를 활용하여 생성된다.
					: IDENTITY 전략을 사용하는경우 persist( ) 하는 즉시 insert 가 날라가야하는 이유 >> 어떤 전략을 사용하건간에 Hibernate 입장에선 영속성 컨텍스트로 엔티티를 관리하려면 Id값을 알고 있어야 하는데, mySQL 과 같은 db에서는 그냥은 다음번 AUTO_INCREMENT된 id 값을 알 수 없고 실제로 insert 를 해야만 얻을 수 있기 때문에, 영속성 컨텍스트에의 저장 요청과 동시에 바로 insert 문을 날리는것이다.

				: 주의 >> 이 전략을 사용하는 경우 애플리케이션단에서 직접 id 를 set 하고, persist( ) 하면 javax.persistence.PersistenceException 와 같은 오류가 발생한다. 
					: GenerationType.IDENTITY 전략을 사용하는 상태에서 ID 필드에 값이 설정되어 있으면, Hibernate 는 이 엔티티가 이미 영속성컨텍스트에 존재한다고 간주하는데 ( 순서가 일단 persist( ) 호출되고 , db로 insert 문 날리고, db 에서 PK 구해오고, 영속성컨텍스트에 저장해놓는거였으니까 ) , 찾아보니까 없어서 에러나는 것이다. 
					: https://stackoverflow.com/questions/72290970/org-hibernate-persistentobjectexception-detached-entity-passed-to-persist-err


			(3) GenerationType.SEQUENCE >>  특정 DB의 시퀀스를 활용하여 Id값을 증가시킴
				: 모든 DB가 시퀀스 객체가 있는건 아니기에, 특정 DB 에 한하여 사용 가능 >>  오라클, PostgreSQL, DB2, H2 데이터베이스
				: IDENTITY 전략과는 다르게, persist 한다고 해서 바로 insert 문이 날라가진 않는다. 단순히 sequence 값만 시퀀스 객체에서 조회해오면되기 때문에, sequence 값을 구하기 위해 ( insert 문이 아닌 ) select 문만 실행된다. 트랜잭션이 다 끝나는 commit 시점에서야 insert 문이 실행된다.


			(4) GenerationType.TABLE >>테이블을 만들어서, DB의 시퀀스를 흉내내는 전략.
				: 모든 데이터베이스에 적용 가능하나, 성능적인 손해가 있어서 잘 쓰지 않는다


    : 엔티티팩토리 관련
	@PersistenceUnit : entityManagerFactory 를 주입시켜준다

	@PersistenceContext : entityManager 주입시켜준다.

	@Transactional : 해당 메서드를 트랜잭션 처리해준다.
